# Pre-probe analysis and prediction note — the Tighten and Typography render seams (written 2026-11-22, before any live probe)

This is a read-only suspicion pass for mission item 3 of BRIEF-SUSPECT3, limited to the two render seams named in the brief. I read ref-php/text-wiki/Text/Wiki/Render/Xhtml/Tighten.php, Parse/Default/Tighten.php, Render/Xhtml/Typography.php, Parse/Default/Typography.php, the render() token-expansion loop in Text/Wiki.php, and the governing parse rules Raw, Rawold, Rawold render, Comment, Colortext, and Iftags; on the mirror side I read Inline3Rules.lean, SeamTypography.lean, InlineRender.lean and SpecXRule.lean. I wrote no probe, touched no ftml file, ran no cargo, set no git identity and made no commit. The only command with side effects on a target was the read-only local reference harness `php ref-php/harness/transform.php render` (it writes no files), used to compute the P_code bytes below exactly rather than by eye; the harness's one trailing echo newline is the programme's usual frame and is not shown in the quoted `<p>…</p>` strings. Sources carry no trailing newline because Wikidot strips one on save. Live Wikidot is definitional and is deliberately not consulted here: every P_code is the reference-as-written output and every P_alt is the competing opposite, written down so the lead can probe and adjudicate. The one surviving empty-rendering token reachable from authored wikitext is the Rawold form `` ``@@x@@`` ``: Raw claims `@@x@@` into a placeholder, Rawold then claims the two-backtick body whose bytes are the Raw placeholder, and Rawold's renderer passes those invalid UTF-8 bytes through htmlspecialchars(ENT_COMPAT, 'UTF-8'), which returns the empty string. This is the same producer that X1/R-XRULE-1 used, and it is the lever for both seams below: at parse time it is a `\xFF<id>\xFF` barrier, at render time it is nothing. A deleted comment is the useful negative control — Iftags::process and the non-indented branch of Comment::parse return the literal empty string, so they remove the barrier before Tighten and Typography run and let the surrounding characters become adjacent (`A [!--x--] B` renders `<p>A B</p>` with one folded space, and `A .[!--x--].. B` renders `<p>A &#8230; B</p>` with the ellipsis formed). The indented-only-line branch of Comment is the other genuine empty-rendering token, but it is line-shaped and awkward to place mid-inline, so Rawold is used throughout.

## Seam T — an empty-rendering placeholder breaks every adjacency test in Tighten's final pass

Tighten runs last (rule 68, ref-php/text-wiki/Text/Wiki.php:132) over source that is a mixture of authored literal text and `\xFF<id>\xFF` placeholders, and all of its shaping decisions are literal-string regexes that require a space to be immediately adjacent to a particular placeholder. The first fold `preg_replace('/[ \t]+/', ' ', $source)` at Parse/Default/Tighten.php:95 (and the identical second fold at line 120) cannot see across a placeholder, which is exactly R-XRULE-1 (`A ``@@x@@`` B` gives `<p>A  B</p>` here, one space on live). The untested part is the three adjacency passes: the Colortext hoist at lines 104-116 (start pattern at line 112, end pattern at line 114), the second fold at line 120 that is supposed to absorb the new run the hoist creates, and the Paragraph/Newline edge trims at lines 127-147 (Newline at 134-135, Paragraph start at 143, Paragraph end at 145). In every case a Rawold placeholder sitting between the named token and the space makes the reference pattern miss, so the reference keeps a space that live's Stage 2 repair (WikiTransformation::purifyHtml, the libtidy pass owned by stage2/BRIEF-TIDY-ORACLE and by R2-PARA/REPORT-R43) plausibly moves or drops. The governing reference lines are Parse/Default/Tighten.php:95, 112, 114, 120, 134-135, 143 and 145, with the token expansion that turns the surviving placeholder into nothing at Text/Wiki.php:1154-1162 and the Stage 2 branch at Text/Wiki.php:1126-1132; the mirror functions are `collapsePad` (Inline3Rules.lean:132-140), `tightenColorPass` (:537-552), `tightenEdgePass` (:558-574) and their composition `tightenBytes` (:580-586), while the already-recorded R-XRULE-1 proposition is `suspect_tighten_folds_residual_run` in SpecXRule.lean:115-116. Every shape below has a same-rule control whose live behavior is already settled by R2-INLINE3 (`##red| A##` = tighten40, `##red|A ##` = tighten41, `a\n b` = tighten14, `____ x` = tighten53, and the plain leading/trailing-space cases), so a single decisive difference isolates the placeholder barrier rather than the underlying space rule.

T-a, color-start hoist blocked by an empty Rawold. Source `A ##red|``@@x@@`` B## C`. P_code: `<p>A <span style="color: red"> B</span> C</p>` — the space stays inside the span because at Tighten time the Colortext-start placeholder is followed by the Rawold placeholder, not by the space, so the line-112 replacement cannot fire; after render the empty Rawold leaves the literal space just after the opening tag. P_alt: live hoists that space out of the color scope and emits `<p>A <span style="color: red">B</span> C</p>` (the hoisted space folding with the following authored space at Stage 2). Reachability: adversarial-only — a raw/invalid-UTF-8 span at the very start of a color body with an edge space.

T-b, color-end eject blocked by an empty Rawold. Source `A ##red|B ``@@x@@``## C`. P_code: `<p>A <span style="color: red">B </span> C</p>` — the space is before the Rawold placeholder rather than immediately before the Colortext-end placeholder, so the line-114 replacement misses and the space remains inside the span. P_alt: live ejects it to after the closer, `<p>A <span style="color: red">B</span> C</p>`. Reachability: adversarial-only, same family as T-a but governing the opposite edge and a different regex line.

T-c, newline edge trim blocked by an empty Rawold. Source `A\n``@@x@@`` B` with one literal newline between A and the backticks. P_code: `<p>A<br />\n B</p>` — the Newline token's following-space trim at lines 134-135 misses because the Rawold placeholder intervenes, so the space after the break survives; the control `a\n b` (tighten14) renders `<p>a<br />\nb</p>` with the space removed. P_alt: live trims the space anyway and serves `<p>A<br />\nB</p>`. Reachability: adversarial-only (an empty raw span starting a continuation line), but it is the smallest discriminator for the Newline half of the edge pass, which X1 and R-XRULE-1 never touched.

T-d, paragraph-edge trim blocked by an empty Rawold; two sources, one mechanism. Source `` ``@@x@@`` A `` gives P_code `<p> A</p>` where the plain control ` A` gives `<p>A</p>` (the Paragraph-start trim at line 143 misses the placeholder); source `` A ``@@x@@`` `` gives P_code `<p>A </p>` where the plain control `A ` gives `<p>A</p>` (the Paragraph-end trim at line 145 misses). P_alt for both: live trims the exposed edge space, serving `<p>A</p>` in each case. Reachability: adversarial-only, but worth both edges because lines 143 and 145 are separate regexes in the reference and separate `dropAfterPh`/`dropBeforePh` calls in `tightenEdgePass`.

A useful paired control for the second fold is `A ``@@x@@`` ##red| B## C`, whose P_code is `<p>A  <span style="color: red">B</span> C</p>`: the color hoist does fire here, the second fold at line 120 collapses the two spaces on the right of the Rawold placeholder but cannot reach the space on its left, so the reference keeps two spaces where live's Stage 2 fold plausibly serves one. It is R-XRULE-1 re-observed after the color pass, not a new mechanism, and is listed so the lead can distinguish a pure adjacency miss (T-a/T-b/T-c/T-d) from a residual cross-placeholder run.

## Seam Y — typography runs over source already carrying 0xFF placeholders

Typography is rule 67, one before Tighten, and Parse/Default/Typography.php applies every substitution directly to `$this->wiki->source` at lines 62-131 while that source still contains all earlier rules' placeholders. The decisive observation is a split by construct. The three quote statements at lines 67-77 use `preg_replace("/``(.*?)''/", …)` and its two siblings, whose `(.*?)` admits `\xFF` bytes, so a placeholder inside a quote pair is carried verbatim into the replacement and survives to render; the mirror's `typoPair`/`lazyClose` (Inline3Rules.lean:292-311) does the same. The French angles at lines 80-83, the digit-space-digit statement at lines 86-87, the number-unit statement at lines 116-120, the ellipsis `str_replace` at lines 122-123 and the two dash `preg_replace`s at lines 126-129 all match fixed literal bytes, and a placeholder is only 0xFF plus ASCII digits, so none of those runs can form across a placeholder: the placeholder is a hard barrier. At render time Text/Wiki.php:1154-1162 expands the barrier to nothing, so the characters on either side become adjacent only after typography has already run. Whether live's own typography is applied before or after its empty raw form collapses is the open question, and the ftml seam adjudication (G1.6, SeamTypography.lean, REPORT-G16, Rule S for a space run crossing a seam and the ellipsis touching a seam) makes "live folds the run" a realistic P_alt, while the PHP reference's placeholder is a native token boundary rather than ftml's structural seam, so the two are not the same mechanism and must be probed rather than assumed equal. Render/Xhtml/Typography.php:24-27 and :46-48 (mirror `renderTypography`, InlineRender.lean:920-952, including the dead `---` arm recorded by SUSPECT-PROSE) only map a char key to an entity and carry no placeholder themselves, so the seam is entirely parse-side. A second, already-settled contrast is that an Iftags-suppressed block or a non-indented comment returns the empty string at parse time, not a token, so its neighbours do become adjacent and typography fires normally (Y5 control below); only a placeholder-bearing token creates the barrier.

Y-a, ellipsis split by an empty Rawold. Source `A ..``@@x@@``.. B` (two dots, empty rawold, two dots). P_code: `<p>A .... B</p>` — four literal dots, because neither the `...` nor the `. . .` str_replace at lines 122-123 can match with the placeholder between the pairs. P_alt: live sees a dot run crossing the suppressed empty token and serves the ellipsis entity, plausibly `<p>A &#8230;. B</p>` (the shape the contiguous control `A .... B` gives here) or `<p>A &#8230; B</p>`. Reachability: adversarial-only, but it is the smallest direct test of "is typography applied to text that contains a placeholder-byte barrier".

Y-b, dash run split by an empty Rawold. Source `A -``@@x@@``- B`. P_code: `<p>A -- B</p>` — two literal hyphens, because the line-126 `--` replacement cannot span the placeholder; the contiguous control `A -- B` renders `<p>A &#8212; B</p>`. P_alt: live joins the run and serves `<p>A &#8212; B</p>`. Reachability: adversarial-only; included because dashes are the other fixed-byte substitution and because the programme has an independent typography-dash finding (F-R2-45, and the dead `---` renderer arm) that makes the dash surface worth isolating.

Y-c, quote/guillemet substitutions carrying a placeholder in their body; two sources, one mechanism. Source `A ``@@x@@'' B` gives P_code `<p>A &#8220;<span style="white-space: pre-wrap;">x</span>&#8221; B</p>`, and source `A <<@@x@@>> B` gives `<p>A &#171;<span style="white-space: pre-wrap;">x</span>&#187; B</p>`; the contiguous controls `A ``x'' B` and `A <<x>> B` give the same entities around a plain `x`. These are the positive half of the answer: the quote statements' `(.*?)` and the angle statements' literal replacement both admit the placeholder and the entity wraps the rendered token output. P_alt: live protects the raw token as a literal range and leaves the authored quotes or angles visible around the raw span, or drops the typography entity at one edge. Reachability: plausible on a real page (a raw span quoted or set off by guillemets), and these are the shapes most likely to be authored by a human rather than constructed for the probe.

Y-d, spaced ellipsis split by an empty Rawold. Source `A . ``@@x@@`` . . B`. P_code: `<p>A .  . . B</p>` — two spaces, because the first fold cannot cross the placeholder and the `. . .` str_replace never sees three contiguous dot-space groups; the cross-placeholder double space is the same Stage 2 surface as R-XRULE-1, here sitting inside a would-be typography run. P_alt: live folds the space and converts the run to an ellipsis, e.g. `<p>A . &#8230; B</p>`. Reachability: adversarial-only; it discriminates the interaction of the two seams rather than either alone, so it is the last probe to spend if the lead is prioritising.

Control Y5, which must agree, is `A .[!--x--].. B` with P_code and P_alt both `<p>A &#8230; B</p>`: Comment deletes to the empty string before Typography, the three dots become contiguous, and the ellipsis fires exactly as on a plain source. If this control diverges, the whole placeholder-vs-deletion account in this note is wrong and the other Y rows should not be interpreted.

## Unreachable and untestable shapes

A probe that tries to place a literal 0xFF byte inside a typography quote, an ellipsis run or a Tighten space run (for example `A ``<FF>'' B`, or `A .<FF>. . B`) is UNREACHABLE/UNTESTABLE with a parse-side reason: every saved source round-trips as valid UTF-8 and 0xFF is not a valid UTF-8 byte, so it cannot be authored, stored or read back by the probe tooling; the only route by which a 0xFF delimiter enters the stream is a rule-created placeholder such as `@@x@@`, which is exactly what the reachable shapes above use. This is the same conclusion the XRULED lane recorded for its Delimiter search, and it is why no literal-byte row is proposed here. Separately, the G1.6 harness block `[[iftags +zz-no-such-tag]]x[[/iftags]]` cannot serve as the PHP-side placeholder: Iftags::process at ref-php/text-wiki/Text/Wiki/Parse/Default/Iftags.php:79-108 returns the empty string for a missing required tag, so on the reference side it deletes to nothing and its neighbours become contiguous — it is the Y5 control dressed up, not a barrier. A genuinely line-shaped empty Comment token can be built with an indented-only comment line (Comment.php:73-89, `A\n  [!--x--]  \nB` renders `<p>A<br />\n<br />\nB</p>`), but its line boundaries make it a poor mid-inline discriminator and it is left unprobed rather than counted as a separate seam. No other reachable rule was found whose token renders the empty string while remaining a placeholder through Typography and Tighten; if the lead wants more samples, vary the Rawold body (`` ``@@y@@`` ``, `` ``@@http://example.com/a@@`` ``) rather than changing the producer.

## Probe order and expected yield

Highest value first: T-a and T-c (they target never-tested regex lines with settled same-rule controls), then Y-a and Y-b (they discriminate the two typography theories), then T-b, T-d and Y-c, then the Y5 control and Y-d. If T-a/T-b/T-c/T-d all match live and X1 does not, the conclusion is that R-XRULE-1's Stage 2 fold is the only Tighten divergence and every adjacency pass already matches live through the placeholder barrier; if any T row diverges, it is a new reference candidate in Parse/Default/Tighten.php at the cited line and the mirror correction belongs in the corresponding `tightenColorPass` or `tightenEdgePass` branch. If Y-a/Y-b diverge, the candidate belongs in Parse/Default/Typography.php's fixed-byte statements (lines 122-129) with the mechanism recorded, not in Render/Xhtml/Typography.php; if Y-c diverges instead, the candidate is the quote pair's placeholder-carrying `(.*?)` at lines 67-83 and the mirror's `typoPair`. No verdict is claimed in this note beyond the reference outputs labelled P_code, which were computed locally before any live probe.
