# H1 — Heading static state across documents in one batch (2026-11-22)

The suspicion was that Heading's anchor counter is process-global, so a later document in one harness batch would inherit an earlier document's final count. The static reading in analysis-toc-heading.md found no such state: Parse/Default/Heading.php:91-106 keeps `headline_id` on the wiki instance, batch.php:60/66/82 allocates a fresh Text_Wiki per case, and the sole PHP static in the Heading family (static $jsOutput in Render/Xhtml/Heading.php:41) is never written and is read only in an unemitted branch. The two observable predictions were written before the probe in LEDGER-M3.md: P_code, a two-case batch A=`+ A1\n+ A2\n+ A3` then B=`+ B1`, gives A toc0/toc1/toc2 and B toc0; P_alt, B continues at toc3.

The local harness probe (h1-batch.json; one `php ref-php/harness/batch.php render` process fed the two JSONL cases, and two separate `php ref-php/harness/transform.php render` runs as the isolation control) gives exactly P_code: batch A ids toc0/toc1/toc2, batch B id toc0, isolation A toc0/toc1/toc2, isolation B toc0. The batch and isolation strings for B differ only by one trailing newline from the harness frame (normalized-equal), not by any heading byte. The real process-global counter artifact of the programme is Math's equationsArray (REPORT-R35.md), which batch.php resets per case; it is not Heading's counter, and it does not reach heading ids.

Verdict UNREACHABLE for a cross-document Heading static leak: the mechanism does not exist in the reference and the only state that could carry it is per instance. The saved-page variant H1c is separately UNTESTABLE at a saved-page oracle, because live Wikidot serves each page in its own request and its own Text_Wiki instance, so two saved pages can never share a counter; the only same-request merge is [[include]], which is within one document and is not a cross-document test. No candidate arises and no reference change is made.
