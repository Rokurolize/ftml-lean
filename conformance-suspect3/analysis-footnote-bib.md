# analysis-footnote-bib — pre-probe suspicion ledger for render-time cross-reference resolution of footnotes and bibliography (2026-11-22)

Scope and method. This is a prediction note only: no live page was fetched, no PHP harness was run, no cargo was invoked, no git identity was set, no commit was made, ftml was not edited, and this is the only file written. Territory is the render-time resolution of the six NOTES rules, i.e. what is decided after the parse tokens exist rather than what the parse patterns claim. Every P_code below is the behavior predicted from the reference as actually written in ref-php/text-wiki/Text/Wiki/ and its Xhtml render tier; every P_alt is the opposite, either the seam defect or the other plausible live shape. All Wikitext sources are given with no trailing newline because Wikidot strips one on save; a literal `\n` inside a source denotes one source newline. Reachability is judged before probing: a shape a real saved page could contain outranks an adversarial-only shape, and any shape that cannot be authored or stored is marked UNREACHABLE/UNTESTABLE with its reason. Where a sibling lane already published a live verdict I say so explicitly as grounding and still restate the two predictions for the new discriminating variant; the new variants themselves are unprobed here.

## The render-time state surface

The reference keeps three document-scoped maps in `Text_Wiki::$vars` (Text/Wiki.php:352) and consults them at render time rather than baking answers into the tokens: `vars['footnotes']` is written by Parse/Default/Footnote.php:48-56 as a positional list with `id = count(footnotes)+1` and read by Render/Xhtml/Footnoteitem.php:60-64 (body indexed by `id-1`) and Render/Xhtml/Footnoteblock.php:39; `vars['bibitems']` and `vars['bibitemIds']` are written by Parse/Default/Bibitem.php:48-50 and read by Render/Xhtml/Bibcite.php:41. The pipeline order that makes this observable is Text/Wiki.php:76-81 — Footnote (76) then Footnoteitem (77) then Footnoteblock (78) then Bibitem (79) then Bibliography (80) then Bibcite (81) — so a footer is assembled at rule 78 from notes already collected at rule 76, and a citation token created at rule 81 is resolved only when the token is rendered, by which time every entry has been registered. The adversarial construct is precisely this: numbering is a counter over distinct keys (`count(bibitemIds)+1`, not a monotonically increasing entry counter), resolution is a byte-keyed map lookup (`bibitemIds[label]`), the footer is a re-injection of stored raw bodies into the source at rule 78, and Text/Wiki.php:1197-1198 runs a regex over already-rendered HTML afterward. The Lean mirror already transcribes these mechanics in NotesRules.lean (`footnotes`/`bibitems`/`bibitemIds` in TokenState.lean:210-219, `bibSet` :86, `footnoteProcess` :152, `footnoteblockProcess` :289, `bibitemProcess` :343, `bibliographyRule` :559, `bibciteScan` :592) and NotesRender.lean (`bibLookup` :64, `renderFootnoteitem` :87, `renderBibcite` :157), including an end-to-end duplicate-label theorem at NotesRender.lean:601.

## S1 — Duplicate bibliography label: id counted by distinct keys while the map value is overwritten (construct no human writes on purpose)

Mechanism: Parse/Default/Bibitem.php:49 computes `$id = count($this->wiki->vars['bibitemIds']) + 1`, so the counter grows with the number of distinct labels, not with the number of definition lines; line 50 then assigns `vars['bibitemIds'][$label] = $id`, which overwrites the value for an already-seen label without adding a key. Render/Xhtml/Bibcite.php:41 reads the final overwritten value and :43-45 emits the not-found span only when the key is absent. Two definition lines with the same label therefore both get footer entries with different displayed numbers, but a later distinct label can reuse the number just consumed by the duplicate, yielding two different labels rendered with the same id; a citation to either label then resolves to that shared number. The Lean mirror states this explicitly in the comment above NotesRules.lean:343 and proves the shape in NotesRender.lean:601 (`a, a, b` registers ids `1, 2, 2` with `a → 2`).

Probe S1a, source `[[bibliography]]\n: a : X\n: a : Y\n: b : Z\n[[/bibliography]]\nCite ((bibcite a)) and ((bibcite b)).`: P_code = three entries render as `1. X`, `2. Y`, `2. Z` (two distinct labels share displayed id 2 and duplicate the DOM id `bibitem-2`), and both citations render the number `2`; P_alt = entries render `1. X`, `2. Y`, `3. Z` and the two citations render `2` and `3`. Reachability: adversarial-only (duplicate labels are not something a human writes deliberately), but every byte is authorable and storable and there are no whitespace-only lines to trip save read-back. Reference: Parse/Default/Bibitem.php:48-50 and Render/Xhtml/Bibcite.php:41-46, Render/Xhtml/Bibitem.php:44-50; Lean mirror: `bibitemProcess` (NotesRules.lean:343-360) and `bibLookup` (NotesRender.lean:64-66).

Probe S1b, source `[[bibliography]]\n: a : X\n: b : Y\n: a : Z\n[[/bibliography]]\n((bibcite a))`: P_code = entries `1. X`, `2. Y`, `3. Z` but the map ends `a → 3` because the third definition overwrites `a`'s value at constant key count, so the citation renders `3` even though the first entry labelled `a` renders `1`; P_alt = the citation renders `1` (first definition wins) or the error span. Reachability: adversarial-only but authorable/storable; this is the shape that separates overwriting-map semantics from first-wins semantics. Reference: Parse/Default/Bibitem.php:48-50 and Render/Xhtml/Bibcite.php:41; Lean mirror: `bibSet` (NotesRules.lean:86-90), `bibitemProcess` (:343), `bibLookup` (NotesRender.lean:64).

Probe S1c (grounded control), source `[[bibliography]]\n: k : First\n: k : Second\n[[/bibliography]]\nCite ((bibcite k)).`: P_code = entries `1. First`, `2. Second` and the citation renders `2`; P_alt = the citation renders `1`. Reachability: adversarial-only but authorable; this is x-bib-dup-label, already probed by the R2-notes lane and reported as ALL3 in conformance-refphp/notes/x-findings.md:11, included here as the control that fixes which of S1a/S1b is the live surface before the new third-label variant is probed. Reference: Parse/Default/Bibitem.php:48-50 and Render/Xhtml/Bibcite.php:41; Lean mirror: theorem `notes_e2e_bibcite_duplicate_example` (NotesRender.lean:601).

## S2 — Forward citation resolves from the final render-time map, independent of token creation order and of placement relative to the definition

Mechanism: Parse/Default/Bibcite.php:46-52 creates a token carrying only the label and performs no resolution; Render/Xhtml/Bibcite.php:41 does the lookup when the token is rendered, so the answer depends on the final map rather than on what had been registered when the token was created. The regex is case-insensitive (`/i`) but the stored keys are the literal matched bytes, so the render-time lookup is byte-exact and a capitalization mismatch produces the not-found span. This is the intended render-time resolution and looks less like a defect than S1, but it is listed here because a parser that resolved at token-creation time instead would diverge, and because the footer re-injection of a footnote body creates a second, later opportunity for a Bibcite token to be born (see S6).

Probe S2a (grounded control), source `((bibcite z))\n[[bibliography]]\n: z : Zed\n[[/bibliography]]`: P_code = the citation resolves to `1` and emits `<a class="bibcite" id="bibcite-1" ...>1</a>`; P_alt = the not-found span `Bibliography item z not found.`. Reachability: very plausible — citing a reference above the bibliography list is normal authoring; live/ftml/reference already agree on this family shape as x-bib-cite-before in conformance-refphp/notes/x-findings.md:11. Reference: Parse/Default/Bibcite.php:46-52, Render/Xhtml/Bibcite.php:41-47, rule order Text/Wiki.php:79-81; Lean mirror: `bibciteScan` (NotesRules.lean:592), `bibciteRule` (:610), `renderBibcite` (NotesRender.lean:157).

Probe S2b, source `((bibcite Alpha))\n[[bibliography]]\n: alpha : lower\n[[/bibliography]]`: P_code = the not-found span naming `Alpha`, because the /i regex claims the citation but `bibitemIds` was keyed by the literal definition bytes `alpha`; P_alt = the citation resolves to `1` as if the lookup were case-insensitive. Reachability: plausible — a capitalized citation against a lowercase label is an ordinary authoring mistake; the sibling lane's probe bibc-case-rev already records this shape in lean-ftml/LeanFtml/SpecNotes.lean:87-105, so this row is a control rather than a new claim. Reference: Parse/Default/Bibitem.php:44-50 and Parse/Default/Bibcite.php:46-52, Render/Xhtml/Bibcite.php:41-45; Lean mirror: `bibLookup` (NotesRender.lean:64-66, byte equality `==`) and theorem `bibcite_not_found` (:500).

Probe S2c, source `[[footnoteblock]]\n[[footnote]]see ((bibcite k))[[/footnote]]\n[[bibliography]]\n: k : Key\n[[/bibliography]]`: P_code = the footer note body renders `see 1`, because the footnote body is re-injected at rule 78 with the literal `((bibcite k))` still in it and Bibcite at rule 81 then tokenizes it, resolving at render from the map that rule 79/80 finished building; P_alt = the footer contains literal `((bibcite k))`, or the not-found span, because the citation was born inside the footer and never saw the later definition. Reachability: adversarial-only (a citation inside a footnote body) but authorable/storable; this is the discriminating variant because the definition is written after the footnoteblock marker, so token-creation-order resolution and render-time resolution disagree. Reference: Parse/Default/Footnoteblock.php:81-83, Text/Wiki.php:78-81, Parse/Default/Bibcite.php:46-52, Render/Xhtml/Bibcite.php:41; Lean mirror: `footnoteblockProcess` (NotesRules.lean:289), `bibciteScan` (:592), `bibLookup` (NotesRender.lean:64), `renderBibcite` (:157).

## S3 — Bibliography ordering is definition order, and only the first block is parsed (limit 1) even when later blocks reuse a label

Mechanism: Parse/Default/Bibitem.php:49 assigns the displayed number from the order in which definition lines are walked, not from citation order or label alphabetical order; Parse/Default/Bibliography.php:36-38 compiles the block with `preg_replace_callback(..., 1)`, so a second block is never compiled and its `[[bibliography]]` opener and `: k : v` lines survive as source text to be claimed by later rules (the sibling lane observed them becoming a definition list). Render/Xhtml/Bibliography.php:44-70 only emits the wrapper and title; it has no ordering or deduplication logic of its own. The adversarial combination not covered by the sibling lane is a second block reusing a label from the first: if limit 1 holds, no new id is registered and a citation to the reused label still resolves to the first block's number.

Probe S3a (grounded control), source `[[bibliography]]\n: z : Zed\n: a : Ay\n[[/bibliography]]\nCite ((bibcite a)) then ((bibcite z)).`: P_code = entries `1. Zed`, `2. Ay` in definition order (not alphabetical and not citation order) with citations `2` then `1`; P_alt = entries in citation order `1. Ay`, `2. Zed`, or alphabetical `1. Ay`, `2. Zed` with citations `1` then `2`. Reachability: plausible — references are commonly listed out of alphabetical order; this is x-bib-unordered-labels, reported ALL3 in conformance-refphp/notes/x-findings.md:11. Reference: Parse/Default/Bibitem.php:49 and Parse/Default/Bibliography.php:58-88; Lean mirror: `bibWalk` (NotesRules.lean:456), `bibliographyProcess` (:542).

Probe S3b (grounded control), source `[[bibliography]]\n: a : Entry A\n[[/bibliography]]\nBetween.\n[[bibliography]]\n: b : Entry B\n[[/bibliography]]\nCite ((bibcite a)) and ((bibcite b)).`: P_code = only the first block is rendered (`1. Entry A`) and the second block stays literal with its `: b : Entry B` line forming a definition list, so `((bibcite b))` emits the not-found span; P_alt = both blocks render and `((bibcite b))` resolves to `2`. Reachability: plausible — two reference lists on one page; this is x-bib-multi-block, whose ftml dump in conformance-refphp/notes/x-ftml-dump-final.jsonl:25 shows the literal second block and the error span. Reference: Parse/Default/Bibliography.php:36-38 and Render/Xhtml/Bibcite.php:41-45; Lean mirror: `bibliographyRule` (NotesRules.lean:559-568) and theorem `bibcite_not_found` (NotesRender.lean:500).

Probe S3c, source `[[bibliography]]\n: a : Entry A\n[[/bibliography]]\n[[bibliography]]\n: a : Entry A2\n[[/bibliography]]\nCite ((bibcite a)).`: P_code = second block literal, no second id registered, and the citation resolves to `1` from the first block even though a second `: a :` line is visible; P_alt = the citation resolves to `2` because the second block registered a fresh id. Reachability: adversarial-ish but authorable/storable; this is the discriminating interaction of limit-1 and label-keyed state that S3a/S3b do not isolate. Reference: Parse/Default/Bibliography.php:36-38 and :61-88, Parse/Default/Bibitem.php:48-50, Render/Xhtml/Bibcite.php:41; Lean mirror: `bibliographyFind`/`bibliographyRule` (NotesRules.lean:522/559) and `bibSet` (:86).

## S4 — Repeated identical citation renders duplicate ids with no per-citation counter

Mechanism: Render/Xhtml/Bibcite.php:41-46 builds the anchor entirely from the looked-up id, so every token with the same label produces the same `id="bibcite-N"` and the same visible number; nothing counts citations. The reference has no deduplication branch and no counter local to the renderer. This is a construct no human would write on purpose in the sense that the output contains duplicate DOM ids, and it is plausible precisely because citing a source twice is normal. Note that live adds a per-page hash suffix to the bibcite id in the serving layer (documented in conformance-refphp/notes/x-findings.md:21), so the observable that matters here is the visible number and the shared numeric prefix, not byte equality of the whole id attribute.

Probe S4a, source `[[bibliography]]\n: k : Key\n[[/bibliography]]\n((bibcite k)) and again ((bibcite k)).`: P_code = both citations render the visible number `1` with the same `bibcite-1` numeric id (duplicate DOM ids up to live's hash suffix); P_alt = the second citation is numbered `2`, or the second occurrence is deduplicated away. Reachability: very plausible — repeated citation of one work is ordinary prose. Reference: Render/Xhtml/Bibcite.php:39-48; Lean mirror: `renderBibcite` (NotesRender.lean:157-169) and `bibLookup` (:64).

Probe S4b, source `((bibcite k)) ((bibcite k))\n[[bibliography]]\n: k : Key\n[[/bibliography]]`: P_code = both forward citations render `1` (same shape as S4a, so placement is irrelevant); P_alt = the first citation is the not-found span while only the second resolves, if resolution were done at token creation. Reachability: plausible. Reference: Parse/Default/Bibcite.php:46-52 and Render/Xhtml/Bibcite.php:41; Lean mirror: `bibciteScan` (NotesRules.lean:592) and `renderBibcite` (NotesRender.lean:157).

## S5 — An opener nested inside a footnote body is not re-matched at the footer (single-pass scan, one closer)

Mechanism: Parse/Default/Footnote.php:44 is one lazy dot-all regex `;\s*\[\[footnote\]\](.*?)\[\[/footnote\]\];s`; its body runs to the first closer, so a second `[[footnote]]` opener inside that body is captured as plain text and is never scanned by the Footnote rule, because that rule has already passed by the time Footnoteblock::parse (rule 78) re-injects the stored body. No later rule claims `[[footnote]]`, so the nested opener survives literally in the footer. Numbering is therefore driven by how many top-level opener/closer pairs the single pass found, not by a recursive block grammar. This is a construct no human writes on purpose but is fully authorable and is the footnote-side dual of the X32 re-injection seam.

Probe S5a, source `[[footnote]]outer [[footnote]]inner[[/footnote]]`: P_code = exactly one footnote numbered `1`, whose footer body is the literal text `outer [[footnote]]inner` (the nested opener still visible, no second note and no second closer anywhere); P_alt = two collected notes numbered `1` and `2`, or the nested opener consumed into a nested note. Reachability: adversarial-only but authorable/storable; a page demonstrating footnote syntax could plausibly contain this. Reference: Parse/Default/Footnote.php:44-59 and Text/Wiki.php:76-78; Lean mirror: `footnoteMatchAt` (NotesRules.lean:141), `footnoteScan` (:164), `footnoteblockProcess` (:289).

Probe S5b, source `[[footnote]]outer [[footnote]]inner[[/footnote]] and [[footnote]]inner[[/footnote]]`: P_code = two notes: note 1 body `outer [[footnote]]inner` (first match ends at the first closer), note 2 body `inner`, with the literal ` and ` staying in the main text between the two footnote references; P_alt = three notes, or note 1 body `outer ` with the inner opener forming its own collected note. Reachability: adversarial-only but authorable/storable; discriminates first-closer lazy matching from recursive nesting. Reference: Parse/Default/Footnote.php:44 and Text/Wiki.php:76; Lean mirror: `footnoteMatchAt`/`footnoteScan` (NotesRules.lean:141/164).

Probe S5c (grounded control), source `A[[footnote]]one[[/footnote]]B[[footnote]]two[[/footnote]]C`: P_code = two separate notes numbered `1` and `2` in source order, collected into one footer; P_alt = a single note or reversed numbering. Reachability: very plausible (two footnotes in one paragraph); this is the ordinary two-note shape already covered by the R2-notes batteries, included as the control for S5a/S5b. Reference: Parse/Default/Footnote.php:48-59 and Parse/Default/Footnoteblock.php:57-83; Lean mirror: `footnoteProcess` (NotesRules.lean:152) and `footnoteblockInside` (:249).

## S6 — Footer re-injection re-matches later line-anchored rules: a bare definition line stays literal but an explicit block opener is claimed

Mechanism: Footnoteblock::process (Parse/Default/Footnoteblock.php:81-83) concatenates each stored note body back into the source, so the body is scanned again by every rule after position 78. Bibitem has no regex and no `parse()` of its own (the mirror proves this as `bibitemRule_id`, NotesRules.lean:621), so a bare `: k : v` line re-injected into the footer is never turned into a bibitem; but Bibliography's `^\[\[bibliography...\]\]` pattern (Parse/Default/Bibliography.php:36, /m) will claim an explicit opener if the re-injected body puts it at a line start, because Bibliography runs at position 80 after the re-injection. The same-looking text therefore diverges solely by whether the explicit block opener is present. This generalizes the established X32 probe in REPORT-SUSPECT-XRULE.md:29 (a table reinjected from a footnote body into the footer is re-matched and gains structure, CONFIRMED there), moving the question from a table to the notes family's own line-anchored rules.

Probe S6a, source `[[footnote]]A\n: k : Key[[/footnote]]`: P_code = the footer body contains the literal definition text `: k : Key` as prose with no numbered `1. Key` bibitem and no bibitem id registered, so a later citation to `k` (not in this source) would be not-found; P_alt = the re-injected line is claimed as a bibliography entry and renders `1. Key` in the footer. Reachability: adversarial-only but authorable/storable; no whitespace-only line, so save read-back should succeed. Reference: Parse/Default/Footnoteblock.php:81-83, Text/Wiki.php:78-79, Parse/Default/Bibitem.php (no regex, base Parse.php:143-151), Parse/Default/Bibliography.php:36; Lean mirror: `footnoteblockProcess` (NotesRules.lean:289) and theorem `bibitemRule_id` (:621).

Probe S6b, source `[[footnote]]A\n[[bibliography]]\n: k : Key\n[[/bibliography]][[/footnote]]`: P_code = the re-injected body is claimed by Bibliography at rule 80, so the footer renders the note body `A` followed by a nested `<div class="bibitems">` containing `1. Key`, and the note itself is numbered `1`; P_alt = the whole `[[bibliography]]...[[/bibliography]]` text stays literal inside the footer with no entry registered. Reachability: adversarial-only (a bibliography block inside a footnote body) but authorable/storable; this is the discriminating pair against S6a because the only difference is the explicit opener and rule 80 runs after re-injection. Reference: Parse/Default/Footnoteblock.php:81-83, Text/Wiki.php:78-80, Parse/Default/Bibliography.php:36-38 and :41-93; Lean mirror: `footnoteblockProcess` (NotesRules.lean:289), `bibliographyFind` (:522), `bibliographyRule` (:559).

## Unreachable and untestable surfaces

The regex over already-rendered HTML at Text/Wiki.php:1197-1198 (`preg_replace_callback("/$d$d(.*?)$d$d/s", array($this, 'strip'), $output)` with `$d = "\x00"`) cannot be driven by any authorable footnote or bibliography source: the sentinel is a NUL pair after correction C-SUSPECT-XRULE-4, and the mirror proves the pass is the identity on any byte list with no NUL (`postStripToc_no_nul`, RenderCore.lean:1171). A shape that smuggles the old authorable `üü` sentinel into a footnote body is therefore UNREACHABLE at the render-time oracle, not a live divergence. The two dead locals in Render/Xhtml/Footnote.php:40-41 (`$label = $options['label']`, which the Footnote token never sets, and `$refs = Text_Wiki_Parse_Math::$equationsArray`, never used) are a process-static read but produce no observable bytes — recorded as vacuous in SpecIntent.lean:913-915 and not probed. `addToken`'s static id counter (Text/Wiki.php:1275-1304) advances across parses and does leak a document-local index through some renderers (the Email family in REPORT-SUSPECT-XRULE.md), but footnote and bibliography displayed numbers come from the document maps, not from token ids, so no authored footnote/bibliography shape can turn that counter into a numbering divergence; those token-index leaks belong to other rule families. A footnote body consisting only of whitespace, or a bibliography body with whitespace-only lines, is apt to fail saved-source read-back the way X5 and X14 did and should be treated as UNTESTABLE at a saved-page oracle rather than as evidence; none of the shapes above use one.

## Probe ordering guidance

Run S1c, S2a, S3a, S3b, S4a and S5c first as controls because each already has a sibling-lane live verdict; they fix the family-shape surface and the frame-level surfaces (raw apostrophe in onclick attributes, bibcite hash suffix, footer newlines) before the new variants are spent. Then spend S1a/S1b, S3c, S2c, S5a/S5b and S6a/S6b, in that order: S1a/S1b test whether live counts distinct keys or definition lines and whether overwriting is observable, S3c tests the limit-1 × label-map interaction, S2c tests render-time resolution across footer re-injection, S5a/S5b test single-pass first-closer behavior, and S6a/S6b test which post-footer rules re-match re-injected text. Compare at family-shape level (ordered footnote numbers, collected item numbers, bibliography entry numbers, bibcite target numbers, presence and text of the not-found span, literal-vs-claimed footer text) rather than byte-for-byte, because the serving-layer hash suffix and the Stage 2 newline/quoting fold are already-owned surfaces. Any confirmed divergence should be stated as a Lean proposition over the existing mirrors named above, not forced onto an unrelated mirror, following the convention in REPORT-SUSPECT-XRULE.md:41-43.
