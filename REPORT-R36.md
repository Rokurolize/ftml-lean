## Byte-form analysis (per rule, before mirroring)

Footnote's pattern is `\s*\[\[footnote\]\](.*?)\[\[/footnote\]\]` with the dot-all modifier, case-sensitive (the R2 exact-case settlement: a mixed-case closer leaves the form literal, which the battery's fn17 shape pins). The opener and closer are ASCII literals and can neither start nor end inside a placeholder; the leading `\s*` consumes the whitespace run before the opener (placeholder bytes are not whitespace, so a run stops at a placeholder exactly as in PHP); the lazy body runs to the first closer and can span whole placeholders, so the stored body is a byte string. Footnoteitem has no source match of its own: its `regex` is null, the base `parse()` skips it, and its tokens are created by Footnoteblock's process; the mirror is the identity, proved as a theorem below. Footnoteblock's `parse()` is a single `preg_replace_callback` with limit 1 over `(\[\[footnoteblock(\s+[^\]]+)?\]\])|($)`: the opener can sit anywhere, its attribute group can span whole placeholders (a title value can be `OptVal.bytes`), and failing any opener the empty end-of-string alternative is the match site, at the very end of the source or immediately before a trailing newline (PCRE's `$` without the multiline modifier). Bibitem likewise has no source match of its own (no `regex`, no `parse()` override); its process is called by Bibliography's walk with one body line at a time, whose bytes can contain whole placeholders, and the stored entry body is a byte string. Bibliography's `parse()` is a single line-anchored block match (`^\[\[bibliography(\s+[^\]]+)?\]\](.*?)\[\[\/bibliography\]\][ ]*$`, multiline and dot-all, limit 1): the body walk's definition and residual lines can contain whole placeholders, which are neither label bytes nor whitespace and so pass through the walk's tests exactly as in PHP. Bibcite's pattern is `\(\(bibcite\s([a-z0-9]+)\)\)` with the /i modifier: exactly one whitespace byte, then a label whose class excludes the delimiter byte, so a label can neither contain nor span a placeholder.

## The disclosed compared-state extension (the second, in the R3.4 pattern)

This family is the first whose rules write and read shared document state beyond the equations map, so the compared state gains three fields, serialized identically on both sides: `footnotes` (the claimed bodies in index order), `bibitems` and `bibitemIds` (the (label, value) pairs in insertion order). The PHP driver (`ref-php/harness/state-restricted.php`) emits them from the live `vars` entries, wire-encoding each byte string exactly as it encodes option values (a body spanning a placeholder crosses as `$bytes`); the Lean serializer (`serState` in `TokenState.lean`, via the new `serBytes` helper) emits them from `DocState`, whose `footnotes`, `bibitems`, and `bibitemIds` fields changed from character lists to byte lists in this stage for exactly this reason (a claimed body is a span of the byte form; no other Lean code used those fields). Per-case isolation follows the batch.php precedent and needs nothing new: the family's state lives in the per-case `Text_Wiki` instance's `vars` (the R2 NOTES harness audit verified it does not leak across cases, and the only process-static on the family's path, Math's equations map, was already reset per case in R3.4). The extension's effect on earlier stages is confined to the wire shape: the R3.1 through R3.5 drivers, rebuilt against the extended serializer, emit the same three fields at their empty values, their comparison copies read missing fields as empty, and the R3.4 and R3.5 slices were additionally verified against their own stages' recorded restricted outputs (382/382 and 221/221 below), so the extension is shown not to move the pre-extension slices on their own records.

## Document-state write and read semantics, as modelled at parse time

Footnote's process initializes the list on first use, takes `id = count + 1`, stores the trimmed body at that index, and claims a token carrying only the id. Footnoteblock's process reads the list and nothing else: with an empty list the match (an opener, or the end-of-string fallback) is replaced by nothing; otherwise it claims, for each note in order, a Footnoteitem start token, the stored body bytes, two newlines, and a Footnoteitem end token, and only then its own start token (with the `getAttrs` title, or null) and end token, wrapped in newlines. The claim order matters and is pinned by the corpus: in the fixtures and on both sides here, the item tokens precede the block's start token in the table while the block's placeholder precedes theirs in the source. Bibliography's process initializes both bibliography vars when `bibitems` is null (the identity on the model's empty initial values) and walks the body: a definition line is preceded by a Bibliography `nl` token when the previous unit was residual, and produces its entry through Bibitem's process; a residual line whose trimmed form is empty is dropped and leaves the walk's classification unchanged; any other residual line is preceded by an `nl` token (after nothing or a definition) or a single space (after residual text), with its whitespace runs collapsed to single spaces; the block's own start and end tokens are claimed after the whole walk. Bibitem's process replaces newlines in the value with spaces, trims, registers the content in `bibitems` under the label, and stores `id = (number of distinct labels so far) + 1` in `bibitemIds` under the label: a duplicate label therefore takes a fresh id computed from the unchanged key count and numbering does not advance for it (the R2 settlement bell, bell, guy → entries 1, 2, 2, with both maps resolving bell to 2), and its start token carries label, id, type, and the empty-body flag (the R2 correction), followed by the content and an end token. Bibcite's parse process reads no state: it claims a token carrying only the label, and the lookup against `bibitemIds` lives in the render rule, outside R3's parse-only scope — recorded plainly, as the same premise correction R3.5 recorded for Equationreference. Footnoteitem's and Footnoteblock's assembly-side R2 corrections (the empty-body separator, the title escaping) are render-side and, as the brief directs, enter here only as the parse facts they ride on: the token shapes above.
