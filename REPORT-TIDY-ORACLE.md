# REPORT-TIDY-ORACLE — the Stage 2 corpus through the local libtidy oracle driven as live drives it

## 1. The oracle driver and how each element of live's binding is reproduced

The reproducible driver is `conformance-tidy-oracle/tidy_oracle.c`, compiled by `conformance-tidy-oracle/build.sh` against the system `/usr/lib/x86_64-linux-gnu/libtidy.so.58`; the four public 5.8.0 headers it needs are vendored under `conformance-tidy-oracle/include/` so a later lane can rebuild without network access. `./tidy_oracle --version` reports 5.8.0. The driver reads one Stage 1 fragment, wraps it, parses and saves it through the libtidy C API, extracts the body, and writes it to stdout or a named output file; the full reproduction recipe is in `conformance-tidy-oracle/README.md`. No ftml was edited, no cargo was run, no repository-local git identity or identity override was set, no live probe page was created, and no Lean build was needed for this lane, so the serial Lean queue wrapper was not invoked.

The wrapper is byte-for-byte the one in `ref-php/fossil/php/utils/WikiTransformation.php:59-74`: the XHTML 1.0 Strict DOCTYPE and `<html xmlns="http://www.w3.org/1999/xhtml" xml:lang="en" lang="en">  <head>    <title>Just A Wrapper</title><meta http-equiv="content-type" content="text/html;charset=UTF-8"/>  </head> <!--wrapdelimiter--><body>` precede the fragment, and ` </body><!--wrapdelimiter--></html>` follows it. The Strict DOCTYPE is not cosmetic: it makes libtidy revert HTML5 content-model changes and parse inline constructs the HTML4/XHTML way, which is the mode every Stage 2 pin was settled against.

The configuration reproduces `tidy_parse_string($c, array('indent' => false, 'output-xhtml' => TRUE, 'wrap' => 0), 'UTF8')` through the C API: `tidySetCharEncoding(doc, "UTF8")`, `indent` set to 0, `output-xhtml` set to yes, and `wrap` set to 0. `indent` is an Enum/Integer option in libtidy 5.8.0, not a Boolean, so the driver calls `tidyOptSetInt` for it exactly as PHP's `ext/tidy` does when it dispatches on `tidyOptGetType`; calling `tidyOptSetBool` there trips a libtidy assertion. `preserve-entities` is additionally set to yes: this reproduces live's preservation of `&#32;`, `&#160;`, `&#8212;`, and `&quot;` where stock 5.8.0 defaults decode them, and it is the configuration difference recorded beside the closed version question in GAP-LEDGER.md's LIBTIDY VERSION GAP CLOSED entry and in TIDY-FINGERPRINT.md section 1.

The call path is `tidyParseBuffer` followed by two `tidySaveBuffer` calls and no `tidyCleanAndRepair`. Call #1 stands in for `ext/tidy`'s `tidy_doc_update_properties()` and call #2 for the cast-to-string in `explode("<!--wrapdelimiter-->", $c2)`; the reported bytes come from call #2. Linking directly against the shared library bypasses the CLI's own repair call, which is why the driver, like live, serves `<a name="anchor-kept"></a>` with no synthesized `id` on p31. Extraction is PHP's own sequence: the bytes between the first two `<!--wrapdelimiter-->` markers, then `str_replace` of every literal `<body>` and `</body>`. A diagnostic run over all 266 cases found tidySaveBuffer call #1 and call #2 byte-identical every time (0/266 differences), confirming the 5.8.0 double-save is idempotent under this wrapper and config, as the version design predicted after the reverted 5.6 regression.

The entity configuration is a real gap in stock 5.8.0, and the control run proves the driver closes it: with `--no-preserve-entities` the oracle matches live on 241 of 266 cases instead of 249, losing exactly eight cases — p28-space-preserved-pre-and-raw, p33-nbsp-vs-numeric-entities, q04-p16-no-uchild, q23-unclosed-div, in2-x42, in2-x55, in2-x58, and con-x17-code-inline-div — and gaining none. With the driver's configured binding those eight cases agree, so the accounting below has no outstanding oracle-configuration gap.

## 2. Three-way tallies over the 266 settled cases

The corpus is the 266 settled Stage 2 cases in `stage2/stage2-evidence/`: battery A (34 authored probes p01–p34), battery B (27 discriminating probes q02–q31), and battery C (205 corpus extractions). For each case the reference Stage 1 render was fed to the oracle, and the oracle output, the retained Lean model output, and the retained live capture were compared after stripping outer ASCII whitespace, the same normalization the Stage 2 reports use. Full per-case records are in `conformance-tidy-oracle/three-way-results.jsonl` and the classified accounting in `conformance-tidy-oracle/classified-results.jsonl`; the scripts that produced them are `three_way.py` and `classify.py` in the same directory.

The tallies are 249 cases in three-way agreement, and 17 cases carrying exactly one classification. Oracle equals live on 249 cases, model equals live on 255, and oracle equals model on 254. By battery: A has 32 three-way agreements, 33 model-live agreements, and 2 classified cases; B has 27 three-way agreements and no classified cases; C has 190 three-way agreements, 195 model-live agreements, and 15 classified cases. All 17 classified cases fall in one class, harness frame, split into 6 script/harness-id cases, 3 dynamic bibcite-id cases, 2 recorded Stage 1 candidates, and 6 recorded frame-compensation cases.

## 3. Every classified disagreement, named by case

### Harness frame: script and harness identifiers (6 cases)

con-x21-div-in-coll-in-tab, con-x22-coll-in-tab, con-x23-div-in-tab, con-x25-tab-in-coll-in-div, con-x29-footnote-in-tab, and lst-x08-list-in-tab. The recorded Stage 1 frame emits two local script tags (`/common--javascript/yahooui/element-beta-min.js` and `tabview-min.js`), a batch-sequential tabview id such as `wiki-tabview-0`, and an inline `(function(){...})()` init body; live serves one CDN `tabview-min.js` tag, a 32-hex tabview id such as `wiki-tabview-f5fefa850c91c6e37c8fa25fd5e66821`, and an OZONE `onDomReady` init body. The oracle and the model both process the recorded frame faithfully and differ from live only in this material; after masking script blocks and normalizing the tabview identifiers, oracle and live are byte-equal on all six. This is the R4-SCOPE framing exclusion recorded in REPORT-STAGE2.md section 4, not a Stage 2 disagreement. For six of them the literal model-oracle equality also fails, but only inside those script and id spans, so root-cause precedence assigns harness frame rather than model gap.

### Harness frame: dynamic bibliography identifiers (3 cases)

lst-x13-deflist-in-bib, lst-x14-deflist-multi-bib, and lst-x15-deflist-bib-colon. The recorded frame carries stable bibcite ids `bibcite-1` and `bibcite-2`; live carries the random hex suffixes `bibcite-1-84754a` and `bibcite-2-79480a`. The oracle equals the model on all three, and after masking the suffixes oracle and live are byte-equal on all three. This is the same dynamic-identifier framing class as above, recorded in REPORT-STAGE2.md section 4.

### Harness frame: recorded Stage 1 candidates (2 cases)

p34-div-tag-attr-whitespace carries C-STAGE2-1: the recorded Stage 1 emits `<div  class="a" id="u-b" style="color:green">`, tidy and the model preserve that attribute order, and live serves `id` before `class`. con-x24-three-nested-divs carries C-STAGE2-2: the recorded Stage 1 renders `<p>[[/div]]</p>` for three same-line div openers, and live serves `<br />\n[[/div]]`. In both cases oracle equals model and both differ from live at the recorded Stage 1 divergence; no tidy configuration connects the two, which is why both were recorded as Stage 1 candidates in REPORT-STAGE2.md section 5 rather than Stage 2 defects.

### Harness frame: recorded frame compensation (6 cases)

p29-unwrap-image-table-dl, in2-x48, lst-x27-deflist-heading, tab-x06-table-in-quote-head, tab-x16-two-adv-adjacent, and tab-x44-malformed-adv-opener. In each, the model equals live and the oracle differs at a paragraph wrapper or a lone sandwiched break: the oracle keeps `<p>lead …</p>` where live serves bare `lead …`, keeps `<p>intro<br /></p>` inside a blockquote where live serves `intro<br />`, or keeps `<br />` between two adjacent tables where live serves the bare newline join. The mechanism is visible in the recorded frame: tidy closes an open `<p>` before a following block but does not unwrap the paragraph or delete a break, so the oracle reproduces the recorded Stage 1 frame under purifyHtml while live serves the frame the Stage 2 model was fitted to. Neither stock tidy nor clean-and-repair performs those unwraps or break drops (both were tested on these shapes), and the 5.4/5.8 equivalence class contains no change of this kind, so these are recorded frame differences, not an oracle-configuration gap or a version-class residue. The model matches live on all six, so the model-gap test is false.

### Zero cases in the other three classes

No case is an oracle-configuration gap after the entity fix, no case is a version-class residue, and no case is a model gap: the model-gap predicate (model differs from both live and the correctly driven oracle on Stage 2-relevant bytes) is false for all 266 cases. The classifier records that predicate explicitly in every row of `conformance-tidy-oracle/classified-results.jsonl`, and `conformance-tidy-oracle/classification-summary.json` reports empty model-gap and unclassified lists.

## 4. Stage 2 model corrections

No file under `stage2/stage2-model/` was changed. Every case where the model differs from live is a recorded harness-frame case, and the four-class definition of a model gap is not met anywhere in the corpus, so there is no case evidence on which a correction could be made. The six frame-compensation cases deserve an explicit note: their model rules (T6 paragraph unwrap and T11 break drop in G2-SCOPE.md) are not libtidy transformations, since the correctly driven oracle does not perform them; they are empirical compensations that make the model reproduce live from the recorded Stage 1 input. Removing them would make the model match the oracle but break its agreement with live, so they are left intact and recorded here as frame compensation rather than presented as tidy behavior.

## 5. Supplementary coverage

As a cross-check outside the 266-case accounting, the 39 remainder probes in `stage2/stage2-evidence/remainder-probes.jsonl` were rendered through the reference harness and driven through the same oracle: 36 of 39 oracle outputs match the retained live capture exactly after outer-whitespace stripping, and the three that do not (u2-root-collapsible, u2-nested-collapsible, and u2-table-then-div) are the same paragraph-unwrap frame compensation seen in the six battery cases above. The artifacts are `conformance-tidy-oracle/remainder-stage1.jsonl` and `conformance-tidy-oracle/remainder-oracle-summary.json`. The single R4-C4 case also agrees three ways, recorded in `conformance-tidy-oracle/r4c4-oracle.json`. These checks are supplementary; the three-way tally and classification are over the 266 settled cases the brief names.
