# REPORT-UFFFD — The U+FFFD collision, decided (2026-11-22)

Lane: UFFFD, under BRIEF-UFFFD.md. The open item from R4-SCOPE.md section 1.1: the reference's `Text_Wiki_Render_Xhtml::pre()` computes `$new_delim = htmlspecialchars("\xFF", ENT_COMPAT | ENT_SUBSTITUTE)`, which is the UTF-8 encoding of U+FFFD (`EF BF BD`), escapes the post-parse source, and then runs `str_replace($new_delim, "\xFF", ...)` to restore the token-delimiter bytes, so a literal U+FFFD character in post-parse literal text is indistinguishable from a converted delimiter and is turned back into `\xFF`, corrupting the delimiter stream. The Lean render core preserves the character. Decision: **MIRROR FINDING**. Live exhibits the collision, not preservation: on live, a literal U+FFFD in prose enters the delimiter stream and corrupts placeholder segmentation in the same mechanism family as the reference's `pre()` conversion, so the Lean core's preservation is the side falsified by live. The finding against the Lean render core is recorded below as C-UFFFD-1. One wording correction to the brief's template: live does not truncate the document the way the fossil loop does; live's parse and render segmentation recovers most of the text and leaks token indices at the corruption points (measured below), while the reference's own render loop, downstream of the same conversion, fatally errors on 29 of the 30 literal-segment cases and garbles the thirtieth. That downstream loop divergence is a separate reference-side remainder (R-UFFFD-1, recorded in section 4), not part of the decided item: the item under decision was the `pre()` conversion itself, and the conversion is live-true. All artifacts are under conformance-ufffd/ (cases.jsonl, cases2.jsonl, cases3.jsonl, captures.json, captures2.json, captures3.json, map.json, maps2-3.json, ref-renders.jsonl, ref-renders2.jsonl, ref-renders3.jsonl, comparison.json). Thirty-six probe pages were created on sandbox-for-codex under the prefixes muse-probe-ufffd-, muse-probe-ufffd2-, and muse-probe-ufffd3- and are kept permanently; every one of the 36 captures is valid, stable, and saved-source-matching. The reference outputs were produced by the worktree's ref-php/ harness (batch.php, render mode) on WSL under PHP 8.5.4; reference outputs carry the usual Paragraph framing (trailing newlines) that live's capture extraction strips, and comparisons below are modulo that framing, as in prior tiers.

## 1. Reachability, route by route

Direct authoring is a live route, and it is the decisive one: live's save layer stores a literal U+FFFD verbatim. Every probe source containing the character round-tripped byte-exactly (saved_source_matches is true for all 36 captures, including plain-only, whose entire source is the single character, and only-two, whose source is two of them). The shape is therefore reachable by any author typing or pasting the character into a page, and no battery case exercising it is a precondition for the collision to matter.

Character references are not a route. Both live and the reference escape the ampersand of `&#65533;` and `&#xFFFD;` in prose (both serve `&amp;#65533;` / `&amp;#xFFFD;`, byte-identical modulo framing), so the reference sequence is never decoded into the character inside the literal stream on either implementation.

Token contents are not a route, and inside them the character is safe on all three implementations. In code-token, the character sits inside a `[[code]]` body, which is token content rather than post-parse literal text; live serves it preserved (`x � y` inside `<pre><code>`), the reference renders it preserved, and the Lean core preserves it. The collision exists only for literal text segments, which is exactly the surface `pre()` operates on. (The raw-token probe is a footnote to this route: live does not tokenize `[[raw]]` in this shape at all and serves the construct literally with the character removed as ordinary prose, while the reference's Raw token path is one of its fatal-error cases; the live output is the literal-stream treatment, consistent with the decision.)

The include route reaches the same literal stream. The Include parse rule is pipeline rule 1, and its expansion is spliced into the document source as literal text before every later rule and before `pre()`, so a U+FFFD authored in an included page enters the including document's literal stream unchanged. The included page itself demonstrates the content side of the route: inc-target serves on live with the collision applied to its own text (`included alpha bravo tail end`, character removed, text recovered). The includer page's capture shows the include construct rendered literally rather than expanded (the target page was created in the same probe batch and live did not fire the include at capture time), so the route's last step rests on the parse-order argument plus the inc-target evidence, and is recorded as such rather than as a directly captured expansion.

File and page metadata, and module output, are not routes into the literal stream. In the reference pipeline, titles, file names, and module results enter as token options and render-side values, never as post-parse literal source text, so `pre()` never sees them; in the Lean model they are `OptVal` values in token entries, equally outside the text segments. Module evaluation on live is deepwell's province and outside this pipeline. A distinct downstream surface exists and is already recorded elsewhere: several fossil renderers call bare `htmlspecialchars`, which can generate U+FFFD in token output from invalid bytes (R4-SCOPE.md section on PHP 8.5 flag sensitivity), but that is after `pre()` and after token expansion, so it cannot collide with the delimiter stream. Finally, invalid UTF-8 bytes in authored source are not a route: live's save layer stores valid UTF-8 (every probe source round-tripped), so the `ENT_SUBSTITUTE`-generated U+FFFD inside `pre()` arises in practice only from the `\xFF` delimiter bytes themselves, which the `str_replace` restore exists to handle.

## 2. What live serves, and what the reference produces

Live never preserves the character in a literal text segment, never crashes, and never truncates the document wholesale. In mid-text positions the character vanishes and the surrounding text and markup survive intact: plain-mid (`alpha � bravo charlie delta`) serves `<p>alpha bravo charlie delta</p>`, near-token keeps both bold spans with the character's segment recovered as text, swallow-bold keeps the bold span that follows the character, inside-bold keeps it inside the emphasis, second-para keeps both paragraphs, heading keeps the heading text, list-item keeps both items' text, and inc-target behaves identically. The spaces-control case confirms live collapses authored multi-space runs in served text (parse-side Tighten behavior), which is why the recovered segments join with single spaces. The corruption becomes visible exactly where the converted byte meets real placeholders. Where the character is the last text before a block end, the following token's index leaks as literal digits: plain-end and plain-only serve `charlie 2` and `<p>2</p>` respectively, end-after-bold and end-no-space serve the same trailing `2`, and end-both-para serves a trailing `4` at its second paragraph. Where the character sits at a block boundary, both adjacent blocks' indices leak and the blocks merge: end-first-para serves `<p>alpha 23bravo charlie</p>` (the two paragraphs collapsed into one, indices 2 and 3 leaked), end-list serves `<li>item one 34item two</li>` (the two list items collapsed), and end-heading serves the body text swallowed into the heading span with `23` leaked. Where the character immediately precedes a token, that token's closing-side index leaks and the token's content degrades to text: fake-before-bold serves `<p>alpha 3bold omega tail</p>` (no `<strong>`, the bold-end index 3 leaked). The enclosed-key shapes show the segment between two converted bytes treated as a would-be token key and emitted as literal text when it names no token: pair-digits serves `alpha 42 charlie delta` and pair-zero serves `alpha 0 bravo charlie`. And only-two, whose whole content is two characters, serves empty output: both bytes consume the paragraph's placeholders and nothing survives. This is the signature of the reference's own mechanism (a literal U+FFFD re-converted to the `\xFF` delimiter and the render segmentation misreading the stream) operating inside live's more recovery-tolerant parse and render segmentation. It is not preservation, and it is not the Lean core's behavior.

The reference, measured through the full pipeline rather than the bare snippet quoted in R4-SCOPE.md, is worse than the recorded truncation: on 29 of the 30 cases with the character in a literal segment, batch.php records the fatal `Error: Call to a member function token() on null`, because the converted byte opens a delimiter span whose key, cast with `(int)`, names a token whose render object is null in the fossil loop. The thirtieth, end-after-bold, survives as garbage (`<p>alpha <strong>bold</strong> <p>1`, a spurious paragraph start and a leaked index). The R4-SCOPE snippet result (`"a � b"` rendering as `"\na "`) is the same mechanism in a token-free harness; the full-pipeline measurement supersedes it. On the six cases with no character in a literal segment (control, spaces-control, entity-dec, entity-hex, code-token, includer), the reference matches live modulo framing, including preserving the character inside code token content.

## 3. The decision and the finding against the Lean render core

The decision is MIRROR FINDING. The premise the decision turns on is settled by the captures in section 2: live's behavior belongs to the reference's mechanism family (the character enters the delimiter stream and corrupts it), and the Lean render core's preservation of the character in literal text is a behavior live does not have. No reference correction is applied in this lane, because the reference's `pre()` conversion, the item under decision, is live-true; and no Lean build was run in this lane, per the brief.

Finding C-UFFFD-1 (against the Lean render core, for the coordinator's mirror work). In `lean-ftml/LeanFtml/RenderCore.lean`, the literal-text path of the render mirror is `xhtmlPreText` (line 445), applied to `.text` segments by `renderSegsLoop` (line 540) under `renderWith` (line 575): it escapes the segment's bytes for `&`, `"`, `<`, `>` and passes every other byte through, so a literal U+FFFD in a text segment is preserved end to end, and the segment model itself (a `TSeg` list of `.text` and `.tok` produced by the parse mirror) gives the character no way to affect placeholder segmentation. Live's rule, which the mirror must adopt, is the reference's: in `Text_Wiki_Render_Xhtml::pre()`, every U+FFFD byte sequence in post-parse literal text is re-converted to the `\xFF` token-delimiter byte by the `str_replace` restore, so the character acts as a delimiter for the render segmentation, with the measured consequences in section 2 (adjacent text recovered as literal output, neighboring token indices leaked as digits at block boundaries and block ends, blocks merged, enclosed digit strings emitted as literal key text). Exactly which mirror function must change: `xhtmlPreText` and the segment consumption in `renderSegsLoop`/`renderWith` in RenderCore.lean, together with whatever parse-side segment construction feeds them, so that a text segment containing U+FFFD is no longer rendered as ordinary escaped text. The evidence is the 36-case family in conformance-ufffd/comparison.json (decisive cases: plain-mid, plain-end, plain-only, end-first-para, end-list, fake-before-bold, pair-digits, only-two), all captures valid, stable, and saved-source-matching.

## 4. Reference-side remainder, recorded and not corrected here

R-UFFFD-1 (reference-side remainder, for coordinator triage). Downstream of the shared conversion, the reference's render loop in `ref-php/text-wiki/Text/Wiki.php` (`render()`: `$key = (int) $key; $rule = $this->tokens[$key][0];` followed by an unconditional `$this->renderObj[$rule]->token($opts)`) diverges from live: it fatally errors on 29 of the 30 literal-segment cases and garbles the thirtieth, where live recovers the text and leaks indices. This lane does not correct it, for two recorded reasons: the item under decision was the `pre()` conversion, which is live-true and unchanged; and matching live here is not a local fix, because live's recovery depends on its own parse and render segmentation and on live's token numbering, which differs from the reference's (in the reference's fresh-document numbering the paragraph-end token is index 1, while live's leaked paragraph-end index in the same shapes is 2). Any future correction must reproduce live's segmentation recovery as its own validated stage, with this lane's 36-case family as its conformance corpus. The Lean mirror consequence is likewise bounded: C-UFFFD-1 obliges the mirror to model the conversion and corruption, and the exact recovery semantics it must reproduce are the ones this remainder names.
