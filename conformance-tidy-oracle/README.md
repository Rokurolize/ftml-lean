# conformance-tidy-oracle — reproducible local libtidy oracle for Stage 2

This directory drives the system libtidy the way live Wikidot's `WikiTransformation::purifyHtml` drives its PHP `ext/tidy` binding, and runs the settled Stage 2 corpus three ways (oracle, Lean model, retained live capture). No ftml was edited, no cargo was run, no repository-local git identity was set, and no Lean build was needed for this lane; the only compiler used is `gcc` for the small C driver. All evidence came from files already in this tree (the frozen battery captures), so no fresh live traffic was generated.

## How live's binding is reproduced

The wrapper is the exact one in `ref-php/fossil/php/utils/WikiTransformation.php:59-74`: `<!DOCTYPE html PUBLIC "-//W3C//DTD XHTML 1.0 Strict//EN" "http://www.w3.org/TR/xhtml1/DTD/xhtml1-strict.dtd"><html xmlns="http://www.w3.org/1999/xhtml" xml:lang="en" lang="en">  <head>    <title>Just A Wrapper</title><meta http-equiv="content-type" content="text/html;charset=UTF-8"/>  </head> <!--wrapdelimiter--><body>` before the fragment and ` </body><!--wrapdelimiter--></html>` after it. The XHTML 1.0 Strict DOCTYPE matters: it makes libtidy parse in HTML4/XHTML mode rather than HTML5 mode, which is the mode the Stage 2 model was settled against.

The configuration mirrors `tidy_parse_string($c, array('indent' => false, 'output-xhtml' => TRUE, 'wrap' => 0), 'UTF8')`: `tidySetCharEncoding(doc, "UTF8")`, `indent` set to 0 (it is an Enum/Integer option, so PHP dispatches `tidyOptSetInt`, not `tidyOptSetBool`), `output-xhtml` set to `yes`, and `wrap` set to 0. `preserve-entities` is set to `yes` to reproduce live's preservation of `&#32;`, `&#160;`, `&#8212;`, and `&quot;` where stock 5.8.0 defaults decode them; this is the configuration difference recorded in GAP-LEDGER.md's LIBTIDY VERSION GAP CLOSED entry and in TIDY-FINGERPRINT.md section 1.

The call path is `tidyParseBuffer` followed by two `tidySaveBuffer` calls, with **no** `tidyCleanAndRepair`. Call #1 stands in for `ext/tidy`'s `tidy_doc_update_properties()` and call #2 for the cast-to-string in `explode("<!--wrapdelimiter-->", $c2)`; the extracted bytes come from call #2. This is also why p31 serves `<a name="anchor-kept"></a>` with no synthesized `id`, unlike stock CLI tidy, which calls the repair pass. Extraction is PHP's own sequence: bytes between the first two `<!--wrapdelimiter-->` markers, then `str_replace` of every literal `<body>` and `</body>`. The driver links directly against `/usr/lib/x86_64-linux-gnu/libtidy.so.58`, bypassing the CLI's repair call entirely.

## Build and re-run

Run `./build.sh` from this directory to compile `tidy_oracle` against libtidy.so.58; the four public 5.8.0 headers are vendored under `include/` so the build needs no network. `./tidy_oracle --version` reports `5.8.0`. To reproduce the accounting, run `./run_all.sh` from this directory (it builds, then runs `python3 three_way.py` and `python3 classify.py`). The first command writes `three-way-results.jsonl` (one record per case with oracle, model, live, and the three equality flags) and `three-way-summary.json`. The second writes `classified-results.jsonl` (each case with its classification, subclass, and evidence) and `classification-summary.json`. `python3 three_way.py --no-preserve-entities` writes the control run (`three-way-results-stock-entities.jsonl`, `three-way-summary-stock-entities.json`) that demonstrates the entity configuration difference.

Driver options are `--no-preserve-entities` (stock-entities control), `--save1 PATH` (dump tidySaveBuffer call #1), and `--raw PATH` (dump the whole saved wrapper from call #2), plus `--version`. Input is one file containing the Stage 1 fragment; output is the extracted body on stdout or a second positional path.

## Files in this directory

`tidy_oracle.c` is the driver source, `build.sh` its build script, `include/` the vendored headers, `three_way.py` and `classify.py` the accounting scripts. `three-way-results.jsonl`, `three-way-summary.json`, `classified-results.jsonl`, and `classification-summary.json` are the core 266-case deliverables. `three-way-results-stock-entities.jsonl` and `three-way-summary-stock-entities.json` are the entity control. `remainder-stage1.jsonl` is the reference-harness render of the 39 remainder probes and `remainder-oracle-summary.json` the supplementary oracle-vs-live result; `r4c4-oracle.json` holds the supplementary R4-C4 check.
