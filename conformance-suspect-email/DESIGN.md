# Pre-probe design: suspicion hunt in the Email family (2026-11-22)

Written before any live probe was created. Reference scope: `ref-php/text-wiki/Text/Wiki/Parse/Default/Email.php` and `ref-php/text-wiki/Text/Wiki/Render/Xhtml/Email.php`; Lean mirror scope: `lean-ftml/LeanFtml/Inline1Rules.lean` (`emailLocalB`, `emailDomB`, `atomChainLen`, `emailMatchLen`, `lazyTail`, `emailDescrMatch`, `emailStandaloneMatch`, `emailRule`) and `lean-ftml/LeanFtml/InlineRender.lean` (`renderEmail`). The fossil shape is only a hypothesis generator; live saved-page behavior is definitionally correct. Each suspicion below carries two observable predictions recorded before probing; where they cannot differ the suspicion is listed as untestable rather than pursued. Evidence order: ftml corpus pins, frozen parity captures, fresh live probes.

S-EMAIL-1 (render, bytewise `strrev($text)`): the renderer reverses the described label byte by byte with no UTF-8 decoding, so a multibyte character's bytes are reordered into an invalid UTF-8 sequence. Prediction A (code is right): a label containing `é` (C3 A9) serves bytes A9 C3 inside the span, which an HTTP text decode shows as a replacement character U+FFFD (or as raw A9 C3), and a CJK label serves its bytes fully reversed. Prediction B (suspicion is right): live reverses by Unicode code point or leaves non-ASCII intact, serving well-formed UTF-8 in the same position. Discriminators: `-lbl-eacute`, `-lbl-emoji`, `-lbl-cjk`, `-lbl-mixed`, `-lbl-acute-only`.

S-EMAIL-2 (render, `str_replace('@','|', …)` over the whole concatenation): the separator replacement is applied to every `@` byte, including an `@` authored inside the described label. Prediction A: `[u@example.com foo@bar]` serves the label half as `rab|oof` with its inner `@` turned into `|`. Prediction B: live only rewrites the address's own `@` (or builds the span structurally), leaving the label's `@` as an `@`. Discriminator: `-lbl-at`.

S-EMAIL-3 (render, literal `#` join and no escaping): the two reversed halves are joined with a raw `#`, and a `#` in the label is neither escaped nor quoted. Prediction A: `[u@example.com foo#bar]` serves two `#` bytes in the span (`…#rab#oof`). Prediction B: live escapes or consumes the authored `#`. Discriminator: `-lbl-hash`.

S-EMAIL-4 (parse, described label is lazy unbounded `.+?`, not the X44 bounded class): X44 converted the interwiki described label into a bounded class but deliberately left Email's `(.+?)` alone. Prediction A (code is right): the label closes at the first `]` at distance at least one even if that `]` is content, so `[u@example.com a]b]` claims label `a` and leaves `b]` literal; a label containing `[`, a URL, or another email is claimed as raw bytes; a newline in the label kills the described match but leaves the bare address claimed. Prediction B (live bounds the email label the same way it bounds interwiki): any label carrying a bracket, a claimed token (URL, email, math) or a newline makes live serve the whole form literal with inner tokens still claimed by their own rules. Discriminators: `-lbl-close-inner`, `-lbl-open-bracket`, `-lbl-url`, `-lbl-email`, `-lbl-strong`, `-lbl-newline`, `-lbl-bracket-lead`, `-lbl-two-forms`.

S-EMAIL-5 (parse, described separator is one literal ASCII space): the regex is `[ADDRESS (.+?)]` with one space, not `\s+` and not `\s*`. Prediction A: a tab or a non-breaking space after the address never forms a described claim (only the bare address is obfuscated); two or three spaces form a claim whose label begins with the extra spaces; a trailing space inside the label survives into the reversed half. Prediction B: live accepts any whitespace run and/or trims the label, so the tab/NBSP forms claim and the multiple-space form has no leading-space artifact. Discriminators: `-gap-tab`, `-gap-nbsp`, `-gap-three`, `-gap-trail`, `-gap-two-trail`, `-gap-control`.

S-EMAIL-6 (frame, trailing space in the reversed label): the frozen capture p07 shows live without the trailing space that the reference emits for `[user@example.com  Double gap]`. Prediction A (code is right, frame explanation): the trim is a page-view edge effect, so when the same shape is followed by other text or wrapped in punctuation the reversed space reappears in both sides. Prediction B (Email-specific explanation): live's label never carries the leading extra space at all (its described regex consumes the whole whitespace run), so the space is absent in every position. Discriminators: `-frame-trail-inline`, `-frame-trail-bracket`, `-gap-control`, `-gap-three`.

S-EMAIL-7 (parse, address grammar boundary): the address is `[_a-z0-9-]+(?:\.[_a-z0-9-]+)*@[a-z0-9-]+(?:\.[a-z0-9-]+)+` with `/i`, so no TLD-length or hyphen-position check, no underscore in the domain, no single-label domain, no consecutive dots, and plus-addressing splits at `+`. Prediction A (code is right): `a@b.c` and `u@example-.com` claim; `u@localhost`, `u@example_com.net`, `u@example..com`, `.u@example.com`, `u.@example.com`, `u@@example.com` do not claim as whole addresses; `u+tag@example.com` claims only from `tag@`. Prediction B: live validates TLDs, hyphen positions, underscores, dots or local part differently in at least one of those shapes. Discriminators: `-addr-minimal`, `-addr-localhost`, `-addr-underscore-dom`, `-addr-double-dot`, `-addr-label-leading-dot`, `-addr-label-trailing-dot`, `-addr-double-at`, `-addr-trailing-dash`, `-addr-leading-dash`, `-addr-plus`, `-addr-tld-digit`, `-addr-upper`.

S-EMAIL-8 (parse, `/i` under byte semantics): PCRE `/i` without `/u` folds ASCII only, and the Lean mirror's `isAlphaB` is ASCII-only. Prediction A: uppercase ASCII addresses claim, but a non-ASCII case-folding character (U+212A KELVIN SIGN, which Unicode folds to `k`) does not count as a local byte; in `éu@example.com` the claim starts after `é`. Prediction B: live folds Unicode or rejects a non-ASCII-adjacent address entirely. Discriminators: `-addr-kelvin`, `-addr-acute-local`, `-adj-acute-before`, `-adj-acute-after`, `-addr-upper`.

S-EMAIL-9 (parse, described pass runs before standalone pass): the described pass consumes the whole bracketed form, so an email inside a claimed label is not separately claimed, and two described forms in one document each claim independently. Prediction A: `[u@example.com other@example.net]` serves one span whose label half is the reversed inner address, with no second span; two forms yield two spans. Prediction B: live claims inner addresses separately or merges the two forms. Discriminators: `-lbl-email`, `-lbl-two-forms`.

S-EMAIL-10 (render, `strrev($email)` for standalone addresses): the visible half and the email half are both byte-reversed, with the dot chain reversed as bytes. Prediction A: `a.b@example.com` serves `moc.elpmaxe|b.a#moc.elpmaxe|b.a` (dots and local separators all reversed together). Prediction B: live reverses only the domain or only the local part. Discriminators: `-addr-dots`, `-addr-minimal`, and the frozen p01/p28 pins.

Untestable by construction (recorded, not pursued): the `options['type']` and CSS configuration branches that Email's renderer never reads; an empty described label (the `(.+?)` requires at least one byte, so `[u@example.com ]` falls to the standalone pass, already pinned by frozen probe p26); and any claim about the client-side JavaScript that reverses the span, because the saved-page HTML is the oracle and the JS is not part of the authored source surface.
