# Pre-probe ledger — suspicion round 4, cross-rule seams (written before any live probe)

Lane territory is the seams between rules, not the per-family ground the sibling lanes are hunting. Every row below was read off the current reference (post REFCORR4, REFCORR5 composite, REFCORR6 source spans) and rendered locally with this tree's ref-php/harness/transform.php before any sandbox create. P_ref is that local render's decisive bytes. P_confirm is the live byte that would make the seam a reference defect. P_clear is the live byte that would mean the reference already matches. Pages will be muse-probe-suspect4c-* on sandbox-for-codex and will be kept. No reference file and no ftml file has been edited. While the first create was in progress, Wikidot's save layer dropped a single trailing newline on toc-adj (read-back was the source without that newline). toc-fn, toc-raw and toc-ufffd were stripped the same way before their create, and the reference render of each stripped source is byte-identical to the render recorded above, because Prefilter adds its own trailing newlines. The case file now holds the save-stable sources.

## S1 — empty Raw token stored as a footnote body (fn-empty)

Seam: Raw runs before Footnote. A body of exactly `@@@@` becomes one empty Raw token whose placeholder is `\xFF<id>\xFF`. Footnote::process stores `trim($matches[1])`, which is that placeholder, and Footnoteitem's renderer emits a separator space whenever `vars['footnotes'][id-1] !== ''`. Tighten later deletes the placeholder from the residual stream, and the empty Raw renderer returns the empty string, so the footer body is blank. The space was decided on a string that both Tighten and the renderer treat as nothing. A human would not keep an emptiness test on the pre-Tighten placeholder. Source `[[footnote]]@@@@[[/footnote]]`. P_ref is the footer fragment `>1</a>. </div>` (space after the period, no body), against the truly empty control `[[footnote]][[/footnote]]` which this same renderer emits as `>1</a>.</div>` with no space. P_confirm: live emits the no-space empty-note form. P_clear: live emits the space, or live still shows the four @ characters. Reachable: a vanished raw span inside a note.

## S2 — spaces around that empty token (fn-ws)

Seam: the same store-then-trim path. Source `[[footnote]]  @@@@  [[/footnote]]`. Raw replaces the run first, so trim sees spaces around the placeholder and leaves the placeholder. P_ref is again `>1</a>. </div>`. P_confirm: live has no space (trim-to-empty after the run vanishes) or keeps the authored spaces as the body. P_clear: live matches the space-and-empty-body form. Same reachability as S1.

## S3 — six-at run inside a footnote (fn-six)

Seam: a run of six @ is one empty Raw token plus two literal @ (REFCORR5 Batch 6). The stored body is the placeholder plus `@@`, which is non-empty, so the space is owed, and the literal @ survive Tighten. Source `[[footnote]]@@@@@@[[/footnote]]`. P_ref is `>1</a>. @@</div>`. P_confirm: live treats the whole run as the empty construct and emits the no-space empty note, or emits a different leftover than `@@`. P_clear: live shows the separator space and the two @ characters. This is the control that isolates S1 to the pure empty token rather than to any @ run.

## S4 — empty Raw token as a bibliography entry body (bib-empty)

Seam: Bibitem sets `'empty' => ($content === '')` on the body after Raw has already substituted, and the renderer prints a space iff empty is false. Source `[[bibliography]]` newline `: lab : @@@@` newline `[[/bibliography]]`. P_ref is `<div class="bibitem" id="bibitem-1">1. </div>` (space, no body). The notes stage pinned a whitespace-only entry as `1.` with no space. P_confirm: live emits `1.</div>` with no space. P_clear: live emits the space, or shows the @ characters. Reachable the same way as S1, on the bibliography side of the same re-injection machinery.

## S5 — Toc NUL sentinels around a heading whose text is only the empty token (toc-adj)

Seam: Heading stores the already-tokenized line, Toc copies that text between item_start and item_end, and those renderers wrap it in a NUL pair that Text_Wiki::strip then passes to strip_tags. Tighten removes the empty Raw placeholder before render, so the four NUL bytes of an empty entry are adjacent (`\x00\x00\x00\x00`). The post-render regex is `/\x00\x00(.*?)\x00\x00/s`. A non-greedy match on adjacent pairs can close on the wrong pair and eat the next entry. Source is `[[toc]]`, a blank line, `+ @@@@`, a blank line, `+ Second`. P_ref keeps both entries: an empty `<a href="#toc0"></a>`, then `<a href="#toc1">Second</a>`, plus an empty `<h1 id="toc0"><span></span></h1>` and `<h1 id="toc1"><span>Second</span></h1>`. P_confirm: live has no empty heading (the vanished run is not a heading) while the reference emits one, or live's second entry is missing or corrupted, or a NUL survives into the page. P_clear: live also emits the empty first heading and a clean Second entry. Adversarial, but it is the neighborhood the NUL-pair correction actually creates.

## S6 — a footnote placeholder copied into the TOC (toc-fn)

Seam: Footnote runs before Heading, so the heading text stored and then copied into the TOC is the footnote-reference placeholder, not the word "body". The same token therefore renders twice. strip_tags on the TOC copy removes the `<sup>` and leaves the digit glued to the title, because nothing in the copied text is a space. Source `[[toc]]` blank line `+ Title [[footnote]]body[[/footnote]]`. P_ref TOC anchor text is `Title1` (no space), while the heading is `Title` plus the footnote sup, and the footer body is `body`. P_confirm: live's TOC entry is `Title` without the digit, or `Title 1` with a separator, or the footnote marker is not duplicated into the TOC. P_clear: live's TOC anchor text is also `Title1`. Plausible on a page that footnotes a heading.

## S7 — raw HTML-looking text inside the NUL pair (toc-raw)

Seam: the heading `+ @@a <b>c</b>@@` is tokenized by Raw before Heading. Toc copies the placeholder. Raw's renderer escapes `<` and `>` and turns the space into `&#32;`, and strip_tags then sees entities rather than tags, so it does not strip them. Source is that heading plus `+ Second` under `[[toc]]`. P_ref TOC text is `a&#32;&lt;b&gt;c&lt;/b&gt;` and the second entry is `Second`. P_confirm: live's TOC entry is the stripped `ac`, or the unescaped tags, or the second entry is damaged. P_clear: live shows the same escaped entry and an intact Second. This is the sentinel neighborhood with a `<` that a human might expect strip_tags to eat.

## S8 — NUL sentinels on the U+FFFD recovery path (toc-ufffd)

Seam: a literal U+FFFD anywhere in the document takes renderLiteralUfffdRecovery, which runs tidy on the fragment before the NUL-pair strip. Tidy is a C program and the sentinels are NUL bytes, so the TOC entry can be truncated at the first sentinel, or the leak digit can change because the heading tokens sit in front of the paragraph-end token the recovery reads as a neighbor. Source is `[[toc]]`, a blank line, `+ Hello`, a blank line, `alpha ` plus U+FFFD. P_ref keeps the TOC entry `Hello`, the heading `Hello`, and the paragraph `alpha <strong>` is not in this source; the paragraph is `alpha 8` (the leaked index is the digit 8). P_confirm: live drops Hello, truncates the page at the TOC, or leaks a digit other than 8 that is not the already-recorded fresh-document offset. P_clear: live also shows Hello in the TOC and the heading, and the leaked digit is 8. The U+FFFD itself is reachable; combining it with a TOC is the seam.

## S9 — composite token shifts the leaked neighbor index (idx, idx-after, idx-base, idx-raw)

Seam: renderLiteralUfffdRecovery, when one literal U+FFFD sits immediately before a placeholder, prints `id - first + 1` and, if another original placeholder follows with nothing between, prints that neighbor's index too and does not render it. The empty Raw token is allocated during Raw, before Paragraph, and Tighten removes its placeholder but not the empty paragraph Paragraph wrapped around it. Those extra tokens are exactly the neighbors the recovery reads. idx-base, source `alpha **bold** ` plus U+FFFD, is the already-settled shape: P_ref is `<p>alpha <strong>bold</strong> 2</p>`. idx, source `@@@@` blank line then that same line, adds the empty Raw (id 0) and an empty paragraph, so the text paragraph's end token displays as 5: P_ref is `<p>alpha <strong>bold</strong> 5</p>` (the empty paragraph does not survive tidy). idx-after, source that line, a blank line, then `@@@@`, puts the empty paragraph's tokens immediately after the leaked paragraph-end, and the neighbor read concatenates them: P_ref is `<p>alpha <strong>bold</strong> 34</p>`. idx-raw, source `@@x@@` blank line then the same line, is the control where the earlier token is a real Raw that live also allocates: P_ref is a paragraph containing the raw span `x`, then `<p>alpha <strong>bold</strong> 5</p>`. P_confirm: on idx or idx-after, live still leaks `2` (the empty construct adds no token and no neighbor) while the reference leaks `5` or `34`; on idx-raw, live leaks a different digit than 5 or drops the raw paragraph. P_clear: idx-base is `2` on live, idx and idx-raw are `5`, and idx-after is `34`. The batteries canonicalized a +1 token-number shift in state dumps; they did not carry this rendered neighbor digit. Reachable wherever a vanished `@@@@` shares a page with a U+FFFD.

## S10 — freelink opened in an included page and closed in the includer (inc-free)

Seam: Include splices `\n\n` plus the included source plus `\n\n` before any tokenization. Freelink's target class is `[^\[\]]`, which includes newlines, and the REFCORR4 delimiter guard does not fire because no earlier token sits inside the brackets yet. The padding newlines therefore become part of the target and are then normalized away. Target page muse-probe-suspect4c-inc-open source `see [[[`. Includer source `[[include muse-probe-suspect4c-inc-open]]` newline `Page]]]`. P_ref is `<p>see <a class="newpage" href="/page">Page</a></p>`. P_confirm: live leaves the brackets literal, split across the include, or links a different target than `page`. P_clear: live also emits the newpage anchor to `/page` with label Page. Adversarial, and it is the include/freelink seam the REFCORR4 guard does not see.

## S11 — included raw inside an unknown module (inc-mod)

Seam: the included page is spliced into the module body before Raw and before Module. Raw turns `@@hello@@` into a placeholder, Module's REFCORR4 path sees the delimiter and re-emits the untrimmed body plus the literal closer, and the include's `\n\n` padding puts that closer in its own paragraph. Target muse-probe-suspect4c-inc-raw source `@@hello@@`. Includer is `[[module nosuchmod]]` newline `[[include muse-probe-suspect4c-inc-raw]]` newline `[[/module]]`. P_ref is the "No such module" error block, then a paragraph whose body is the raw span `hello`, then a paragraph whose text is `[[/module]]`. P_confirm: live consumes the body (error block only, no raw span and no closer) or keeps the closer on the same line as the raw span. P_clear: live shows the error, the raw span, and the closer in the following paragraph, modulo the usual error-block frame newline. This is the include-shaped form of the XRULE-3 path, which was pinned for a code token written directly in the body, not for an included raw with the splice padding.

## S12 — include padding splitting a blockquote (inc-bq) and padding meeting a leading blockquote (bq-start)

Seam: Blockquote is the first rule of the block family and its regex requires a newline before `>`. Prefilter supplies that newline by prefixing `\n` and suffixing `\n\n`, then compressing runs of three or more newlines to two. Include's own `\n\n` wrap plus that compression inserts a blank line between an included quote line and a quote line in the includer, so the two lines become two blockquotes. A quote written directly as `> quoted line` newline `> next line` is one blockquote with a `<br />` in this same reference. Target muse-probe-suspect4c-inc-quote source `> quoted line`. Includer `[[include muse-probe-suspect4c-inc-quote]]` newline `> next line`. P_ref is two blockquotes, `quoted line` and `next line`. bq-start source `> quoted` (no leading newline in the authored source) depends on the synthetic leading newline: P_ref is one blockquote containing `quoted`. P_confirm: live joins the included line and the following line into one blockquote, or bq-start is not a blockquote. P_clear: live also emits two blockquotes for the include and one for bq-start.

## S13 — the empty token delivered by an include, then the index leak (inc-idx)

Seam: the same neighbor-index read as S9, but the empty Raw token is created from an included page rather than from the includer's own source. Includer `[[include muse-probe-suspect4c-inc-emptyraw]]` blank line `alpha **bold** ` plus U+FFFD. P_ref is `<p>alpha <strong>bold</strong> 5</p>`, the same digit as idx. P_confirm: live's digit differs from idx's live digit, or differs from 5 when idx itself matched 5. P_clear: live's digit equals both 5 and idx's live digit.

## S14 — included raw inside a known css module (inc-css)

Seam: the same splice as S11, but css is a module the harness treats as available, so the renderer emits the module marker with the body urlencoded. The stored body is still the Raw placeholder (`%FF0%FF` once encoded), and the REFCORR4 re-emit still appends the raw span and the literal closer because the delimiter test is not limited to unknown modules. Includer `[[module css]]` newline `[[include muse-probe-suspect4c-inc-raw]]` newline `[[/module]]`. P_ref contains the marker, then the raw span `hello`, then a paragraph `[[/module]]`. The marker-versus-`<style>` difference is the serving layer and is not the seam. P_confirm: live's style block does not contain a doubled raw span after it and does not leave `[[/module]]` literal, or the style body is the authored `@@hello@@` rather than a rendered raw span. P_clear: live shows a style element and also the raw span and the literal closer after it. The doubled output is what the unconditional re-emit produces.

## S15 — freelink-guarded raw reinserted into the footnote footer (fn-free)

Seam: `[[[@@x@@]]]` is tokenized by Raw before Freelink. The REFCORR4 guard returns the whole match literal, Footnote stores that literal including the placeholder, and Footnoteblock reinserts it where later rules do not get another freelink pass. Source `[[footnote]][[[@@x@@]]][[/footnote]]`. P_ref footer is `1</a>. [[[<span style="white-space: pre-wrap;">x</span>]]]`. P_confirm: live builds a freelink in the footer, drops the brackets, or leaks an index. P_clear: live shows the same literal brackets around the raw span. This is the placeholder surviving into the footnote machinery after the freelink guard has refused it.
