# REFCORR6 design decision — the Mathinline source-text mechanism (2026-11-22)

The live rule settled by the SUSPECT3 sixteen-case battery is raw-body preservation: Mathinline emits the trimmed authored `[[$ ... $]]` body verbatim, expanding every earlier-rule placeholder back to that token's original source text recursively, and emits an empty body (`$$`) when a Freelink, Raw, Newline or Image token occurs anywhere in the expansion, at any depth. The reference's Mathinline rule cannot derive that rule from its token table as it stood: each `Text_Wiki::addToken` entry held only `[rule, options]`, and the one-level option fold in `Parse/Default/Mathinline.php` therefore substituted a described email's label, dropped its address and brackets, and leaked a nested placeholder as replacement bytes.

Chosen mechanism (a): carry each token's original source text from `addToken` onward in a side table on the wiki object. The decisive evidence is in `Text/Wiki/Parse.php::parse()` and in every rule that overrides `parse()`: `preg_replace_callback` invokes `process($matches)` with `$matches[0]` as the exact full matched source and the groups in the remaining slots, and the `addToken` calls sit directly inside those callbacks. The claimed span is available at the call site, often as a group rather than `$matches[0]` — `Url::process` claims `$matches[3]` and returns `$matches[1]` and the trailing bytes outside the token, `Newline::process` claims only the LF after its `$matches[1]` prefix, and `Code::process` claims `$matches[0]` minus its trailing whitespace group. Passing that precise span as a fourth, optional `addToken` argument is a one-line edit per call site, changes no rule order, and leaves the pipeline's sixty-eight rules in place.

The side table, not a third element in the token array, is essential. `state-restricted.php` serializes `$wiki->tokens` verbatim and `TokenState.lean::serToken` emits the two-element `[rule, options]` shape; adding a field to the compared token array would move every state record in r43, r44, r45, r46, r48 and CAPSTONE for no live-visible reason. A parallel `Text_Wiki::$tokenSource` array is read only by the Mathinline expansion, so the correction is observable exactly where live differs.

Rejected alternatives: (b) per-rule source-text reconstruction at Mathinline time can be made to reproduce the sixteen battery shapes from option values, but it is a heuristic inverse of each rule's parse, not preservation of authored bytes. It cannot in general recover a described email's exact brackets, an Image attribute order, or a Code opener's authored arguments from the normalized option map, and it would need a new reconstruction table every time a rule's options change; it is used only in the Lean mirror, whose token entries are structural and whose option values fully determine the source for every rule that can reach Mathinline. (c) a pre-tokenization capture pass over `[[$ ... $]]` bodies changes pipeline order for all sixty-eight rules and would require re-adjudicating every stage gate; the battery needs no such reordering because the source text is already in hand at each `addToken` call.

A fourth possibility, capturing `$matches[0]` through a `debug_backtrace()` inside `addToken`, was rejected as fragile: it still cannot pick the claimed group out of the match, it breaks for the scanner-based Raw and custom-pass rules, and it hides a rule-dependent decision inside a shared choke point.

The suppression set is exactly the four battery-proven rules {Freelink, Raw, Newline, Image} at any depth. Depth is bounded by a cycle guard on token ids, and a token with no recorded source degrades to the old one-level option substitution rather than leaking new bytes. The six SUSPECT3 MATCH rows (plain, url, email-bare, raw, newline, two-urls) are regression pins on both sides.
