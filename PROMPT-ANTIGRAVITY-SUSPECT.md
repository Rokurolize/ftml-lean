You are auditing the PHP reference implementation of Wikidot's Text_Wiki pipeline in the working tree `~/.local/state/wikijump/muse-bhl/lean-ftml-antigravity-suspect/` on this machine. The tree holds: `ref-php/` (the reference: a fossil Text_Wiki codebase corrected rule by rule until it differentially matched live Wikidot across roughly ten thousand battery cases), `lean-ftml/` (a Lean 4 mirror of the reference, parse tier and render tier, byte-exact against it on every gate), `conformance-refphp/` (the differential batteries and their live captures), `stage2/` (the post-render repair model record), and `GAP-LEDGER.md` / `R4-SCOPE.md` (the programme's accounting).

## The idea you are being asked to execute

The reference has been validated by batteries: large, but batteries only test the shapes someone thought to generate. You are asked to validate it the other way around, by reading it the way a skeptic reads inherited code. Read the implementation closely. Wherever a construct makes you stop and think "would a human writing this today write it this way? For what purpose?", treat that as a hypothesis: either the fossil encodes a real behavior of live Wikidot that no battery has pinned yet, or it is a fossil artifact that live does not share, and the battery shapes simply never discriminated the two. Your job is to discriminate, with live probes aimed exactly at the suspicious construct, and then to write down the correct specification in Lean.

Concretely, for each suspicion you find, anywhere in the 68-rule pipeline (parse or render side):

1. Record the suspicion: the file and construct, what the code does, why it looks wrong or arbitrary, and the two observable predictions (what live serves if the code is right; what live serves if the suspicion is right). If the two predictions cannot be made to differ observably, say so and move on; untestable suspicions are listed, not pursued.
2. Design the smallest live probe that discriminates the predictions and run it on the sandbox (tooling: `cd ~/.agents/skills/wikidot-py-operations && scripts/wikidot-python scripts/wikidot-probe create/capture` against site `sandbox-for-codex`, page prefix `muse-probe-agy-suspect-`, pages kept permanently). A capture counts only when it is valid, stable, and source-matching. Fetch once, cache, reuse.
3. Run the reference on the same source (`php ref-php/harness/batch.php` here on this machine) and compare byte by byte.
4. Verdict: CONFIRMED (live matches the reference; the strange code is live's real behavior), DIVERGENCE (live differs; give the differing bytes and the minimal correcting change you would make, but do not apply it), or UNREACHABLE (the suspicious path cannot be triggered from authored page source; give the argument).
5. For every CONFIRMED suspicion, and for any DIVERGENCE where you can state live's true rule from the probes, write the specification as a Lean proposition in a new file `lean-ftml/LeanFtml/SuspectSpec.lean`: a statement about the Lean mirror's functions (which mirror this reference one to one) that expresses the pinned behavior, with the probe page names in a comment above it. Attempt the proof where it is within reach; where it is not, leave the statement with the proof marked as an explicit `sorry` AND flag it in your report as an unproven specification, never silently.

## Discipline

Live Wikidot behavior is definitionally correct, however malformed. The fossil code's shape is never evidence of anything; it only generates hypotheses. Evidence order when sources disagree: a fresh valid source-matched live probe outranks frozen captures, which outrank the reference's current behavior. Do not modify any existing file in the tree; your only writes are `REPORT-ANTIGRAVITY-SUSPECT.md`, `lean-ftml/LeanFtml/SuspectSpec.lean`, and your probe artifacts under `conformance-agy-suspect/`. If you build Lean to check a statement, use `export PATH="$HOME/.elan/bin:$PATH"` and `LAKE_JOBS=1`, one invocation at a time.

## Deliverable

`REPORT-ANTIGRAVITY-SUSPECT.md` in the tree root, ending with the exact line COMPLETE or PARTIAL: (naming what remains). It contains: the full suspicion ledger in the order you pursued them (construct, both predictions, probe pages, capture validity, verdict, differing bytes where any), the list of untestable suspicions with reasons, and an index of the Lean specifications you wrote (statement name, what behavior it pins, proved or unproven). There is no quota on suspicions and no reward for a long list: a short ledger of sharp, well-discriminated suspicions is worth more than a long list of vague ones. The coordinator will re-verify your decisive captures firsthand before anything is adopted.
