## What was built

The three mirrors live in a new module, `lean-ftml/LeanFtml/FormRawRules.lean`. Raw's parse() in the corrected reference is a hand-written byte scanner (the fossil regex in the file is retained only for inventory tools), and it is translated mechanically, statement by statement: the previous-byte lookbehind, the maximal opener and closer runs, the run-of-3+ pre-check that a closer exists before the next newline, the collapse and unterminated branches, the cross-line branch with its trimmed one-line body (empty becoming a single space), the newline abort, and the run-length arithmetic for pure `@` runs and for extra `@`s on either side (Nat subtraction reproduces PHP's `max(0, …)` clamps exactly). Form and Rawold go through the base class's `preg_replace_callback`, so their mirrors are explicit backtracking enumerations in PCRE's priority order, in the style of the Code mirror: Form's pattern `/\[\[form\]\]\s*\n(.*?)(?:\n---\s*\n(.*?))?\n\[\[\/form\]\]/is` is enumerated as greedy `\s*\n` candidates (the whitespace run's newline positions, last to first), lazy group 1, and at each group-1 length the separator group present (its own `\s*\n` greedy, group 2 lazy) before absent; only the match extent is computed, because process() uses $matches[0] alone. Rawold's `/(?<!`)``([^']*[^`])``/U` is enumerated by growing the apostrophe-free prefix one byte at a time, an apostrophe being admissible as the body's final byte but never inside the prefix. Form's process() claims one Form token per line of the match (`text`, or `blank` = 1 for an empty line) with the placeholders rejoined by newline bytes; Raw and Rawold claim their body as `text`. The runner (`LeanFtml/Pipeline.lean`) gained the `.form`, `.raw`, `.rawold` RuleId constructors, their applyRule cases, and `pipelineR32`; `pipelineR31` is unchanged. The driver `lean-ftml/ConformanceR32.lean` follows the R3.1 pattern (same JSONL protocol, same input-stage CRLF normalization) with one addition described below, and is registered as the `lean-ftml-conformance-r32` executable in lakefile.toml.

## The byte-form obligation, discharged per rule

These are the first rules whose pipeline position follows a token-producing rule (Code), so the obligation recorded in TokenState.lean and REPORT-R31.md binds: a mirror written against the segment view alone would be a stage failure even if the corpus passed. In the reference, each of these rules operates on the whole current source as a byte string, placeholders included: Raw's parse() scans `$this->wiki->source` directly, and Form and Rawold run through the base class's `preg_replace_callback` over the same string. All three mirrors therefore work on the state's byte form: `applyByteRule` (FormRawRules.lean) takes the state to `byteForm`, applies the byte-level rule, and splits the rewritten byte string back into segments at well-formed placeholders, the same recovery the PHP state driver performs. Placeholder bytes are inert during matching (no pattern here can match byte 0xFF, a digit, `@`, a backtick, an apostrophe, a newline, or any literal byte of the form delimiters in the wrong place); the live question is only whether a placeholder can end up inside a claimed text, and that differs per rule. The evidence is a dedicated probe set, `conformance-r3/probes/` (16 inputs, both drivers' outputs, and the comparison, 16/16 with three cases unrepresentable on both sides), plus the fuzz mixture family below.

Raw: the byte-form view is needed (its input can contain placeholders anywhere), but a claimed body provably never contains one. The only placeholder producers ahead of Raw in this pipeline are Code and Form (Delimiter never claims: it is the identity on decoded text, R3.1's `delimiterRule_id`). Every Code placeholder is immediately preceded by a newline byte (Code's replacement text is `"\n\n"` before the placeholder), and a Form block's placeholders are joined by `\n`, so each of them is immediately preceded by a newline except the block's first, which is instead immediately followed by a `\n` join (a form block always has at least two lines). A body Raw claims is newline-free: the newline-abort branch rejects any body containing `\n`, and the cross-line branch claims only the trimmed remainder, which contains no `\n` either. So a claimed body cannot contain a Code or later Form placeholder (the preceding `\n` would be inside it), cannot start at one (the opener run would have to end exactly on the byte before it, which is a `\n` or body text, never the second `@` of an opener), and cannot contain a Form block's first placeholder either: starting there means the `\n` join follows inside the body, and ending exactly there would require the closer `@@` to sit where the `\n` join sits. The probes confirm the mechanism from the outside: `@@start\n[[code]]x[[/code]]\nend@@` aborts across the code placeholder and leaves both `@@` literal around the Code token (probe f3, reference record shows exactly the Code token and literal `@@`s); `@@[[form]]…[[/form]]@@` likewise leaves the `@@`s literal while Form claims its lines (probe g1); and where code markup sits inside a raw span without a line start, Code never claims it and Raw claims the literal markup as its text (probes e1, e5), while a run of four `@`s around a code block collapses to plain text with no token at all (probe e6). Raw token texts therefore always decode as text, and the mirror's `textVal` never takes its bytes branch for this rule.

Form: the byte-form view is needed, and claimed lines can be placeholder bytes. A code block claimed at a line start inside a form block leaves its placeholder alone on a line, because Code's replacement pads the placeholder with newlines on both sides; that line is then claimed by Form as a line whose bytes are exactly the placeholder (probe f1: `[[form]]\n[[code]]x[[/code]]\n---\ny\n[[/form]]`). Form lines can also contain a placeholder mid-line when the code block shares the line. Both shapes are real states of the reference, and the protocol disposition is the next section. The remaining probes pin the matcher itself: the opener and closer match case-insensitively with case preserved in the token texts, blank lines claim `{blank: 1}` (probe g4), a separator with an empty data section works (g5), and with two `---` lines the first is the separator and the second is data (g6).

Rawold: the byte-form view is needed, and bodies can span placeholders, because the body class `[^']` admits newlines and placeholder bytes alike. A body spanning a code placeholder (probe f2) or form placeholders (probe g2) is claimed by the reference with the placeholder bytes inside its text; same disposition as Form. Bodies that contain code markup without a placeholder (the markup never claimed, because it is not at a line start) are ordinary text (probe e4's family, also fuzz-covered).

## The unrepresentable-state protocol

A Form or Rawold token text containing placeholder bytes is a PHP byte string that no `List Char` can hold, so TokenState.lean gained one additive constructor, `OptVal.bytes : List Nat → OptVal`, for exactly this value shape, and the mirrors' claim helper produces it whenever a claimed text contains byte 0xFF. Such a state is real in the reference but cannot cross the conformance protocol: the PHP state driver's `json_encode` fails on the placeholder bytes and the driver emits `{"id": …, "error": "json_encode failed: Malformed UTF-8 characters, possibly incorrectly encoded"}` for the whole case (this is the reference's own record for probes f1, f2, and g2). The R3.2 Lean driver intercepts any state containing a `bytes` value and emits the identical record, and the stage copy of compare.py (conformance-r3/compare.py, extended for this; the R3.1 copy in conformance-r3-prev/ is untouched) counts an error record on both sides as a pass printed `PASS-UNREPRESENTABLE`, and an error record on exactly one side as a failure. The interception condition coincides exactly with the PHP failure condition: segment texts are always valid UTF-8 (every rule's match boundaries fall at ASCII bytes, never inside a multi-byte sequence), so `json_encode` fails if and only if a token option contains placeholder bytes. In the fuzz runs below, 55 of 500 cases (default seed) and 50 of 500 (seed 7) were unrepresentable on both sides, with the per-side error counts identical, so the disposition is exercised heavily rather than being a corner nobody hits.

## Theorems

Two theorems were proved in FormRawRules.lean and added to Main.lean's audit block. `utf8Bytes_no_ff : 0xFF ∉ utf8Bytes c` states that no character's UTF-8 encoding contains the placeholder delimiter byte (lead bytes top out at 0xF4, continuations at 0xBF), which is what licenses splitting byte strings at delimiter bytes in both the model and the PHP driver; its audit line reads `'LeanFtml.utf8Bytes_no_ff' depends on axioms: [propext, Quot.sound]`. `rawScan_no_at` states that on a source with no `@` byte, Raw's scanner is the identity (no opener can start, every byte is copied, no token claimed); its audit line reads `'LeanFtml.rawScan_no_at' depends on axioms: [propext, Classical.choice, Quot.sound]`, the choice entering through the full simp used in its induction step, the same class as R3.1's `byteForm_text`. Neither theorem depends on `sorryAx`. Beyond these, the three rules admit no cleaner proved characterization at this grain (their content is the scanners' branch structure itself), so exhaustive conformance (corpus, 1,000 fuzz cases, 16 probes) is the evidence, as the brief's G1.6 precedent allows.
