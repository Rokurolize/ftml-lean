## Per-mechanism byte-form analysis: Image

The reference pattern is `/(\[\[((?:f)?[<>=])?image\s+)(.*?)\]\]/is`: an opener `[[`, an optional alignment group, the word `image` case-insensitively, a whitespace run, and a lazy body to the first `]]`. The alignment group's candidates in PCRE order are the f-prefixed form, the bare form, and absence; the `/i` modifier covers the `f` as well, so the prefix byte may be uppercase `F`, and the recorded alignment keeps the matched bytes (the corpus case i37-10-uppercase-align pins exactly this, align `F>`). The whitespace run after `image` is greedy-maximal, so the body is exactly the bytes between the end of that run and the first `]]`, with no backtracking freedom anywhere: a shorter or longer whitespace run could move the first `]]` only if the run itself contained `]]`, which whitespace cannot. The mirror enumerates the three alignment candidates in order and takes the first that completes, which is the reference's own search. process() first returns the match literal when the whole match contains a delimiter byte (correction C7: a raw-token head, or any earlier rule's placeholder inside the would-be image, makes the opener literal); because of that bail, every Image option value in this mirror is a plain string, never a `$bytes` value, since no claimed value can span a placeholder. The body splits at the first space byte: with no space the whole body is the source and the attribute map is empty; otherwise the tail goes through the base class's `getAttrs` (the R3.5 byte mirror `getAttrsBytes`, reused unchanged) and only the whitelisted keys are copied, in the fixed order title, link, style, class, alt, height, width, size, with the size value lowercased. A link starting with `*` loses the star and sets the target to `_blank`; a link whose first byte is a `ctype_space` byte (space, tab, LF, VT, FF, CR, the same byte set as PCRE `\s`) makes the whole match literal (correction C3); a link containing `://` must satisfy the reference's URL pattern or the match is literal, and the Wikilink-disabled branch after it is a no-op in the source (its return is commented out), so it is not mirrored. The URL pattern is an unanchored, case-sensitive `preg_match` for one of the schemes http, https, ftp, gopher, news, then `://`, then a host part whose decisive property is reachability: after any number of `label.` groups (a label is one or more bytes outside the excluded set: dot, PCRE whitespace, `/`, `"`, `'`, `<`, `\`, the delimiter byte, and the control bytes 0x01-0x1A), a byte in `[a-z]` must occur. The label run is deterministic, since a label cannot contain the dot that ends it, so host reachability is a simple recursion in the mirror rather than a search. The alignment option is set from the opener group when present, a source starting with `*` loses the star and sets the target (an option assignment in the reference, so a target already set by the link star keeps its earlier position, which the mirror's option construction reproduces), and the replacement is the placeholder padded with `"\n\n"` on both sides when an alignment is present.

## Per-mechanism byte-form analysis: Newline

The reference pattern is `/([^\n])\n(?!\n)/m`: a byte that is not a newline, a newline, and a negative lookahead for a second newline. The scan is deterministic position by position: a match at byte `b` exactly when `b` is not 0x0A, the next byte is 0x0A, and the byte after that is not 0x0A or the input ends. process() returns the captured byte followed by a Newline placeholder with empty options, and the newline byte itself is consumed. The byte-form reading matters twice over: the captured "character" is a single byte, so a match can start at a UTF-8 continuation byte, and the byte before a newline can be a placeholder's delimiter byte, so a Newline claim can follow a placeholder directly; the Prefilter's padding (the source is wrapped in a leading newline and a trailing blank line, with runs of three or more newlines compressed to two) means most real line breaks are in fact consumed by Paragraph matches instead, and Newline claims are the residue the paragraph pattern leaves, which is exactly what the corpus shows. The mirror is a one-pass scan with a two-byte lookahead, which is the pattern itself, with no enumeration anywhere.

## Per-mechanism byte-form analysis: Paragraph

The rule runs in two passes. The preparation pass, `tokenizeScoredSpans`, applies the pattern `/(\xFF-unit*)\[\[span_([^\]]*)\]\](.*?)\[\[\/span\]\](\xFF-unit*)/is` globally, where a unit is a single space, tab, CR, or LF byte or one whole placeholder; matches are computed on the pre-pass source and spliced without rescanning, in preg_replace_callback semantics. The lead unit run is greedy with backtracking (longer leads are tried first), the attribute group runs to the first `]`, the body is lazy to the first case-insensitive `[[/span]]`, and because the trail unit run is greedy-maximal at the end of the pattern, the first closer always completes the match, so the body is deterministic given the lead; the mirror enumerates lead lengths in descending unit order and takes the first completion, which is the engine's own search, and no exponential case arises (the enumeration is over the lead run's unit splits only, each tried once). The callback inspects the lead and trail runs: a run has a break when it contains an LF or CR byte, or a placeholder whose current token, in the table as it stands when the callback runs (the table grows as callbacks claim Span tokens), is a Newline token; a run with a break is replaced by only its non-Newline placeholders concatenated, dropping every literal whitespace byte and every Newline placeholder, and a run without a break is kept verbatim. The pair itself is `Span::process` with the attribute text prefixed by one space, mirrored by reusing the R3.8 byte mirror `spanProcess` unchanged: it claims the Span start and end tokens and returns the spliced pair, or nothing when the trimmed content and the arguments are both empty; when the pair is non-empty the rule records it in its scored-span table under the start token's index. The main pass is preg_replace_callback with `/^.*?\n\s*?\n/m`: a match at a line start is unique, because the lazy first line must reach the line's newline (or be empty for an empty line) and the lazy whitespace run after it ends at the first newline inside it, while a whitespace run containing no newline cannot complete the match at that start; matches therefore always end just after a newline and the scan resumes at a line start. process() returns the empty string when the trimmed match is empty; when the match starts with a delimiter byte it reads the first token's key and returns the match unchanged when the key is a scored span whose recorded pair trims to the same bytes as the match, or when the token's lowercased rule name is in the skip list (blockquote, code, clearfloat, heading, horiz, deflist, table, tableadv, list, toc, center, tabview, div, the four divalign forms, collapsible, note, math, module, module654, footnoteblock, footnoteitem, bibliography, bibitem, gallery, image); otherwise it claims a Paragraph start token and an end token and returns the start placeholder, the trimmed match, the end placeholder, and `"\n\n"`. The reference's scored-anchors branch, which reads a variable only the unmirrored Anchor rule's parse sets, is dead in any pipeline without Anchor (the restricted pipeline, and any prefix of it), and a grep of the stage corpus confirms no case carries a `[[a_` shape, so the branch is documented in the mirror's header and not mirrored; it becomes live only when Anchor is mirrored, the same retirement condition as the h18-anchor exclusion from R3.7. Settled in the brief and not reopened here: the space-run collapse is a Stage 2 purifyHtml behavior (Tier 2), not part of this rule.

## Paragraph mirror versus the G1.5 ParagraphStack model

The two Lean models of paragraph formation were compared directly, and no difference was found that constitutes a divergence between them within either model's claim boundary; the three differences that do exist are layer differences, each already dispositioned on the G1.5 side, and they are recorded here rather than silently preferred away. On the core shape the models agree exactly: a nonempty plain-text run closed by a blank line becomes exactly one paragraph wrapper on both sides (the reference claims one Paragraph start/end pair around the trimmed run; G1.5's claim C1 makes a nonempty `current` flushed by `end_paragraph` into exactly one `Paragraph` container), an empty or whitespace-only run produces no wrapper on either side (the reference returns the empty string; C1 makes an empty flush a no-op), and trailing whitespace of a run appears inside the paragraph on neither side (the reference trims the whole match before splicing it between the wrapper tokens; G1.5's claim C5 trims the pending run's trailing spaces). The first real difference is segmentation: the reference decides by run, so a blank-line-delimited run whose FIRST token is skip-listed stays entirely unwrapped, including plain text later in the same run, while the G1.5 stack decides by element, so a paragraph-unsafe element first flushes the pending paragraph and is placed in `finished`, and following safe elements accumulate into a fresh run that will be wrapped (claim C2). These are different segmentations of the same byte stream, but they are not two answers to one question inside either claim set: G1.5's claims are conditional on the operation stream the ftml driver issues, the driver never presents the stack with the reference's run structure (ftml's own parsing decides element boundaries upstream), and no case in either conformance corpus contradicts the other's claims within its own boundary, since the R3.11 corpus's skip cases exercise the reference side only and the G1.5 grid never generates the reference's run shapes. The second difference is the scored span: the reference's wrapper suppression is driven by its own preparation pass inside this rule, while on the ftml side the nearest analogue is the stack's unwrapped-flush mark (claim C6), a driver-issued signal; the scored-span mechanism itself is not an operation the G1.5 model exposes, and its grid excludes the shape, so this is a scope difference, not a disagreement. The third difference is images: G1.5 explicitly excludes them (its candidate finding F-G15-3 records the dedicated image arms as unmodelled, and its disposition list defers the aligned-image separator mark), while this mirror covers the parse-claim side, where an aligned Image token is itself in Paragraph's skip list; the ftml-side image and paragraph interaction shapes from the R2 record were adjudicated there as Stage 2 surface, so the two models' surfaces are disjoint by construction. Bottom line: the Paragraph mirror and the ParagraphStack model agree on every shape both can express, and the differences are the run-versus-element segmentation boundary, the scored-span preparation, and the excluded image arms, all of which sit in the driver layer G1.5 dispositions as outside its claims; no new finding is raised by this comparison.
