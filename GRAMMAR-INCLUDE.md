## The unit

`include(input, settings, includer, invalid_return)` performs ONE expansion pass over the input (recursion into fetched content is the caller's business, not this function's). If `settings.enable_page_syntax` is false it returns the input unchanged with no pages [CODE mod.rs]. Otherwise it returns the rewritten text and the list of fetched PageRefs in input order.

## Scanning (which ranges are candidates)

S1. Candidates are found by a multiline, case-insensitive regex anchored at line starts: `^(?:[ \t]*>)*\[\[include\s+` [CODE]. So a block must begin at the start of a line, optionally preceded by spaces/tabs and `>` quote markers, and the word include is case-insensitive. S2. The opener is TIGHT: no whitespace between `[[` and `include` [GRAMMAR comment: "Live rejects any whitespace between [[ and include"]. The corpus pins the same at parse level: test/include/wikidot-argument-whitespace contains `[[ include ...` and `[[\tinclude ...` as non-include shapes [PIN]. S3. After `include` comes `\s+` (regex) / `whitespace` = spaces, tabs, newlines, one or more (grammar.pest) — the page reference may sit on a following line [GRAMMAR][CODE]. S4. The candidate end is the FIRST `]]` at or after the match that is followed by `\n`, `\r\n`, or end of input (find_include_end) [CODE]. The scan for it is not quote-aware and not comment-aware. S5. If no such terminator exists, scanning stops: the rest of the input is left untouched [CODE].

## Block grammar (unquoted candidates)

G1. Form: `[[` ci-`include` whitespace page_ref, then optionally whitespace, an optional stray-bracket run, and an argument tail, then `]]` immediately followed by newline-or-EOF (lookahead) [GRAMMAR]. The grammar's newline is pest's NEWLINE: `\n`, `\r\n`, or a lone `\r`. This is WIDER than the candidate end of S4 (`find_include_end` accepts no lone `\r`): at a `]]\r` the block parse succeeds and the scan resumes at the parsed end, stepping inside the wider candidate end [DIFF: conformance-g14 grid case term-cr-then-other, 2026-11-20]. G2. page_ref: optional `:site:` prefix. site chars exclude space, newline, tab, `[`, `|`, `]`, `:`, `"`, `'`. page chars exclude space, newline, tab, `[`, `|`, `]`, `"`, `'` (colons allowed, so category:page works) [GRAMMAR]. The parsed PageRef must be non-empty after validation (validate_include_page_ref) [CODE]. G3. Stray open brackets: between the page reference and the arguments, a run of `[` (not starting a comment `[!--`) plus optional single space is tolerated and discarded [GRAMMAR comment: four imported corpus pages rely on this, all a bare `[[` on the line after the page reference; live renders their arguments and shows no bracket]. G4. Argument tail: everything up to the block end. Segments split on raw `|` bytes; a pipe splits even inside quotes [GRAMMAR comment] and inside comment spans. Comments carry no special status during segment scanning: `[!-- ... --]` bytes are ordinary tail bytes, a pipe inside a comment splits the segment there, and an unterminated comment is ordinary text that cannot fail the block [LIVE: AUDIT lane probes muse-probe-audit-g14b-cmt-pipe and muse-probe-audit-g14b-cmt-unclosed, 2026-11-21, audit-g14b/captures.json; cmt-pipe substitutes the value `[!-- a` with the remainder `b --]HELLO` inert, and cmt-unclosed expands normally with the value `[!-- unclosed`]. The earlier claim that comments are skipped during segment scanning and that an unterminated comment fails the block came from ftml's parse.rs scan_include_arguments [CODE] and is REFUTED by those probes. G5. Each segment is `key = value` (key end found by scan; segments without a valid key are inert and ignored, and an inert segment does not disturb duplicate handling) [CODE]. Values are the raw segment bytes, comment bytes included, trimmed at the edges with the live PHP trim set [LIVE: the same audit probes; a value may consist of or contain `[!-- ... --]` bytes, which the fold substitutes literally, as in muse-probe-audit-g14b-cmt-val-only]. The earlier clause that values do not cross comments rested on ftml test names [CODE: include_argument_values_use_the_live_php_trim_set, include_argument_trim_does_not_cross_comments] and is superseded by the same evidence. G6. (FTML IMPLEMENTATION ONLY, superseded as spec by X1-X4 below.) ftml resolves argument values that reference other arguments as {$name} by bounded recursive map expansion (growth checked before copying; cycles bounded; unresolved references left as-is) [CODE parse.rs expand_argument_expression*]. Live adjudication (2026-11-20, conformance-g14b/RESULTS.md) shows live does NOT do this: see finding F-G14B-1. The block-level grammar above does not depend on either semantics. G7. A first tail segment that is empty with only spaces/tabs after the pipe is recorded as a flag (spaced_empty_separator) [CODE test: parse_include_block_records_only_the_live_spaced_empty_ separator_shape]. Its consumer is the parser's include element, outside include() itself. G8. Dotted host site names in the `:site:` slot are canonicalized [CODE test: parse_include_block_canonicalizes_dotted_host_site].

## Reference resolution (page_ref text → PageRef)

R1. The grammar's page_ref run is resolved by `PageRef::parse_include` (src/data/page_ref.rs): the run is trimmed (`str::trim`); a leading `:` requires a second `:` with a non-empty site between them (`:foo` and `::page` are parse errors, so the block stays literal) [CODE; DIFF grid]. LIVE CORRECTION (2026-11-20, L6 below): as a statement about LIVE this is false for the two leading-colon shapes. Live accepts `:foo` and `::page` as includes of the stripped page name (`foo`, `page`). R1 as written is ftml's behavior; the live rule for these shapes follows the fossil's disposition (leading colons stripped, ref treated as a plain page). Finding F-R2-1. R2. The page part is split at the first `#` or `/` (`split_page`); the remainder is an undisplayed extra that never appears in the Display form, so `page/edit` fetches and reports `page` [CODE; DIFF grid]. R3. A site segment in host form `<slug>.wikidot.com` (case-insensitive suffix, one optional trailing dot, prefix of [A-Za-z0-9-]+) is canonicalized to `<slug>` before normalization (`canonical_include_site`) [CODE; DIFF grid]. R4. Site and page are slug-normalized by wikidot-normalize 0.12.0's `normalize`, in this order: trim; strip one leading `/`; NFKC; case fold; replace each character outside [\p{L}\p{N} `-` `:` `_`] with `-`; merge every colon except the last into a dash; replace each underscore that is not at the start and not immediately after a colon with a dash; strip leading/trailing dashes; collapse dash runs and colon runs; remove dashes adjacent to colons (`:-`, `-:` → `:`) and next to underscores (`_-`, `-_` → `_`); strip leading/trailing colons; strip a leading `_default:` prefix [CODE, crate source; DIFF grid for the ASCII fragment]. R5. The resolved reference displays as `:{site}:{page}` or `{page}`; that Display string is the includer key and the value reported in include()'s page list. An empty normalized page is a parse error [CODE; DIFF grid].

## Quoted candidates (the non-fetch rule)

Q1. If the line prefix before `[[` contains at least one `>`, the candidate is parsed as a QUOTED include: following lines are stripped of the same quote prefix (same depth, spaces/tabs around each `>`), the normalized text is parsed as an unquoted block, first bounded by the candidate end, then by the whole remaining region [CODE quoted.rs]. ADJACENCY CONDITION (adjudicated 2026-11-20, see L1 below): the scanner regex itself must span the prefix, so the `>` run must be IMMEDIATELY adjacent to `[[` (spaces/tabs allowed before each `>`, none between the last `>` and `[[`). The spaced form `> [[include ...]]` never forms a candidate at all: it is ordinary blockquote text on both live and ftml. Note the asymmetry: continuation lines during normalization DO allow spaces around each `>` (strip_quote_prefix skips horizontal space), only the first line is tight. Q2. A quoted include that parses is CONSUMED AND DELETED from the output and is NEVER fetched and never appears in the returned pages [CODE mod.rs consumed_quoted_ranges; E SKILL.md: "consumed without being fetched on purpose (Wikidot parity)"]. Q3. A quoted candidate that does not parse under either strategy falls back to the ordinary path (treated by the unquoted parse from the line start, which will normally fail and leave the text literal, resuming the scan at the candidate end) [CODE].
RESOLVED 2026-11-20 (finding F-G14-1, ftml PR #1531): the quoted-consumption mechanism Q1-Q3 describe no longer exists in ftml. PR #1531 deleted src/includes/quoted.rs and narrowed the scanner regex to the unquoted line-start form only, so a `>`-prefixed line is never a candidate: it is never fetched and never deleted by the include pass, and reaches the parser as ordinary text (at top level the parser's quote-line handling still shows nothing, inside a native blockquote the quote row consumes it, and inside [[code]] the literal bytes survive, matching live in each context). Q1-Q3 are retained above as the verified record of the removed mechanism. The Lean conformance driver was updated to the no-consumption scan and the grid re-verified 119/119 against ftml 97bed049d; the quoted-normalization theorems in IncludeGrammar.lean carry a retirement note to the same effect. The remaining quoted shapes were probed live the same day (conformance-g14/evidence-q2/, pages muse-probe-g14q-*): inside [[code]] the nested tight, nested spaced, and indented forms all stay literal; as native blockquote lines the nested tight form renders nothing, the nested spaced form renders a blockquote holding the literal include text, and the indented form renders as literal paragraph text; no shape expands.

## Parse failure and resumption

F1. An unquoted candidate whose block parse fails, or whose reference resolution fails, is left as literal text; scanning resumes at the next line start after the failed candidate's opener line [LIVE: probe muse-probe-audit-g13-f1-bad-next-good, whose first line `[[include bad.page` stays literal while the second line's include expands; AUDIT-G13, 2026-11-21]. F1's previous text (scanning resumes at the candidate end) was [CODE]-derived from ftml's mod.rs and is refuted by that probe: resuming at the candidate end swallows a valid include beginning on an intervening line, because the failed candidate's end can lie past that line's start. F2. After a successful block, scanning resumes at the block end [CODE]. Ranges therefore never overlap and are strictly increasing.

## Fetch

H1. All parsed (unquoted) includes are fetched in ONE includer.include_pages call, in order [CODE]. H2. If the returned count differs from the requested count, or any returned page_ref differs from the requested one, include() returns invalid_return() [CODE]. (E excludes this path.)

## Substitution (the splice)

U1. Replacements are applied in REVERSE range order to the original string, so earlier offsets stay valid [CODE]. U2. A fetched page with content: the content first undergoes variable substitution ({$name} replaced by the include's argument values; unknown names are left literal) [CODE replace_variables]. U3. A missing page is replaced by includer.no_such_include(page_ref) [CODE]. U4. Padding: if the replacement text is non-empty, exactly one line ending is inserted before it when the range does not start at offset 0, and exactly one after it when the range does not end at the input end. The inserted ending is `\r\n` when the adjacent input text uses `\r\n` there (prefix side: input before the range ends with `\r\n`; suffix side: input after the range starts with `\r\n`), else `\n` [CODE substitute_replacements; E property 5]. U5. An empty replacement, and every consumed quoted range, is a pure deletion of the range [CODE; E property 3]. U6. The returned pages are exactly the fetched refs, in input order (the reverse pass collects them reversed, then the list is reversed back) [CODE; E property 2].

## What E proves vs what this spec adds

E (2,000,719 inputs, ≤5 tokens, 4 includers) proves include() does not panic, asks for and returns the right pages RELATIVE TO ITS OWN parse, deletes only when nothing is inserted, is the identity when nothing is asked, and pads per U4. E explicitly does NOT state which text counts as a block (S1–S5, G1–G8, Q1–Q3 above), does not cover variable substitution results (U2 beyond defined names), Wikijump layout, the settings gate, or the invalid_return path (H2). Those are this loop's G1.3/G1.4 remainder.

## Argument substitution (the live rule; G1.4b, 2026-11-20)

Evidence: 14 sandbox probes (conformance-g14b/, all captures valid and saved_source_matches=true; e1 re-verified by direct anonymous fetch). Target content slots A/B/M observed through live renders.

X1. Substitution into fetched content is a fold over the argument list IN SOURCE ORDER (inert segments and empty-valued arguments skipped, per the G1.4 segment rules). For each (key, rawValue), every occurrence of the literal text `{$key}` in the current content is replaced by rawValue. X2. Values are used RAW: a value's own `{$...}` text is inserted literally and is only ever rewritten if a LATER argument's key matches it (e1, e2, e7, e10, e11, e12, e14). Keys are never expanded (e3). X3. Duplicates: a later duplicate fires iff its placeholder still occurs in the content at its turn (consumed in e9; the empty first value in e13 never consumed it; reintroduced by the first value in e14, where the second then rewrites the inserted text). X4. No recursion, no budget, no self-reference special case in the observable rule: a self-referential value replaces the placeholder with itself (e4), cycles resolve to whatever the fold leaves (e5), undefined references stay literal (e6).
