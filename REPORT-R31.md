# R3.1 report: token-state infrastructure, the restricted state bridge, and the Prefilter, Delimiter, and Code mirrors

Stage R3.1 of the ftml Lean equivalence loop is complete. The stage built the token-state model that every later R3 stage builds on, the restricted-pipeline PHP state driver and comparison tool (bridge A of R3-SCOPE.md), mirrors of the first three parse rules in pipeline order (Prefilter, Delimiter, Code), and the parse-rule vars inventory the scope asked for as a by-product. The final conformance corpus is 77 cases (the 68-case R2 Code battery plus the 9-case R2 smoke battery), with zero exclusions, and the Lean model matches the restricted PHP reference on all 77 cases and on 1,000 additional adversarial fuzz cases. No live probing was used, ftml was not touched, nothing was published, and all work is inside this worktree (`~/workspace/ftml-lean-equivalence-r3-1/`); the canonical record at `~/workspace/ftml-lean-equivalence/` was only read.

## The representation decision

The parse state is modelled as a segment list: the working source is a `List TSeg`, where a segment is either a run of text (`List Char`) or a token reference carrying the token's per-document index, and the token table is a `List TokenEntry` in claim order, each entry a rule name plus an ordered option map (`OptMap`, an association list whose `omSet` reproduces PHP array assignment semantics: overwrite in place, append if absent). Alongside the working source and token table, the state carries the document variables structure (`DocState`, below) and the harness-provided page information. Two alternatives were considered and rejected, and the reasoning is recorded in the header of `lean-ftml/LeanFtml/TokenState.lean`. A sentinel-character model (a reserved character standing for the delimiter byte) was rejected because the reference's delimiter is byte 0xFF, which is not a Unicode scalar value and so has no `Char`; any stand-in character (U+00FF being the obvious candidate) genuinely occurs in decoded text, so a rule scanning for the sentinel could fire on real text where the reference cannot fire, and a rule could equally produce the sentinel as data. A byte-level model (working source as UTF-8 bytes) was rejected because the harness protocol only ever carries decoded text (the JSONL drivers transport strings; a raw 0xFF byte cannot even be expressed in the input), so the byte level is unobservable in every differential this loop can run, while taxing every rule mirror with UTF-8 bookkeeping. The segment model keeps placeholders structural, which makes the strongest frame fact true by construction: text a rule produces can never be mistaken for a placeholder by a later rule. The one obligation the choice creates is recorded in the same header: a rule that runs after placeholders exist in the real pipeline must be written against the byte-form view of the state (the concatenation of text segments' UTF-8 encodings and `\xFF<index>\xFF` placeholder encodings, provided as `byteForm`), because the reference's byte-oriented regexes can in principle anchor inside what the model sees as text. The three rules mirrored in this stage all run at token-free positions on any input the harness can express, so the obligation does not bind yet; it binds from the first rule whose pipeline position follows a token-producing rule, which is exactly where R3.2 will start.

## What was built

On the Lean side, `lean-ftml/LeanFtml/TokenState.lean` holds the infrastructure: the character classes the reference's own primitives use (PCRE `\s`, PHP `trim`'s default set, which differ: PCRE whitespace includes form feed, PHP's trim set includes NUL and vertical tab but not form feed), the option value and map types, the segment and state structures with their canonicalization (`normSegs`: no empty text segments, no adjacent text segments), the token-claim operation (index = current table length), the byte-form view with its one proved lemma (`byteForm_text`: the byte form of a token-free state is the UTF-8 encoding of its text), and the canonical JSON serializer both bridges share. `lean-ftml/LeanFtml/FrameRules.lean` mirrors Prefilter as six composed steps in the reference's exact order (CRLF to LF, CR to LF, whitespace-only lines emptied under the multiline pattern `/^\s+$/m`, tabs to four spaces by plain replacement rather than tab stops, the `\n` prefix and `\n\n` suffix padding, and the newline-run compression `/(\n[]*){3,}/` to exactly `\n\n`, modelled through the pattern's group structure), and Delimiter as the identity on states, with the argument below. `lean-ftml/LeanFtml/CodeRule.lean` mirrors Code: since Lean has no regex engine, the rule's pattern is an explicit backtracking search enumerating matches in PCRE's priority order (see the semantics notes below), and `process()` and the base class's `getAttrs` are modelled from their sources, with PHP's `stripslashes` modelled from probed behavior. `lean-ftml/LeanFtml/Pipeline.lean` is the runner: its `RuleId` type enumerates exactly the mirrored rules, so a pipeline cannot silently stand in for an unmirrored rule, and `pipelineR31` is the reference's rule list restricted to `[prefilter, delimiter, code]`. `lean-ftml/ConformanceR31.lean` is the model-side driver in the Tier 1 pattern (JSONL `{"id","source"}` on stdin, canonical states on stdout; its hand-rolled JSON string parser handles `\uXXXX` including surrogate pairs, and the input edge applies exactly the PHP drivers' CRLF normalization, reusing the Prefilter mirror's own first step). The new executable is registered in `lean-ftml/lakefile.toml` as `lean-ftml-conformance-r31`.

On the PHP side, `ref-php/harness/state-restricted.php` is the restricted state driver: it takes a comma-separated rule list, constructs `new Text_Wiki($rules)` with only those rules in order (the in-tree precedent is batch.php's Include-only construction), sets the same harness page variable as the other drivers, applies the same input normalization, and emits the canonical segment/token JSON per case, with token ids left as the reference's process-global ids for the comparison tool to renumber. `conformance-r3/compare.py` is the comparison tool: it canonicalizes both sides identically (token ids renumbered per document in table order with segment references rewritten, segments normalized, option maps compared as unordered key sets with scalar values compared as strings after the JSON round-trip, an empty PHP array equalling an empty map), and prints a per-case verdict and a summary count rather than only an aggregate. `conformance-r3/consistency_check.py` is the restricted-vs-full consistency check described next, and `conformance-r3/fuzz_r31.py` is the fuzz differential described below.

## The restricted-vs-full consistency check and the final corpus

The differential's corpus is the 77 R2 cases (68 Code battery, 9 smoke), whose existing full-pipeline state fixtures are pre-seeded in this worktree as `conformance-r3/expected-code-states.jsonl` and `conformance-r3/expected-smoke-states.jsonl`. Before comparing the Lean model against the restricted reference, the stage checked that the restriction itself is sound for these rules: `conformance-r3/consistency_check.py` compares, per case, the Code tokens claimed by the restricted pipeline (`Prefilter,Delimiter,Code`) against the Code tokens in the full-pipeline fixture, under the same canonicalization as the main comparison. The result is agreement on all 77 cases (68/68 code, 9/9 smoke), so the exclusion files `conformance-r3/exclusions-code.json` and `conformance-r3/exclusions-smoke.json` are both empty and the final corpus is all 77 cases with zero exclusions. Two facts make the agreement structural rather than accidental on this corpus, both verified directly from the fixtures: no case's full-pipeline table contains an Include token (Include runs first and its expansion is plain text), and in every case that has Code tokens, the first Code token sits at table position 0, so at Code's pipeline position the source is token-free on every decodable input in any pipeline configuration, not only in the restricted one; Typography's constant tokens are registered by a rule that runs long after Code and so cannot disturb Code's claims.

## Semantics notes (what the mirrors had to get right)

The Code pattern's body is `((?:(?R)|.)*?)` followed by the closing tail, and the recursive alternative re-runs the whole pattern, `^` anchor included. PCRE evaluates that anchor against the whole subject at the recursion's entry position, so a recursive match can only start at a line start. This is observable in both directions within this stage's own evidence: in the battery case `[[code]]\n[[code]]\ninner\n[[/code]]\nouter\n[[/code]]` the inner block starts at a line start, the recursion fires, and the outer body spans the inner closer; in the fuzz case `[[CODE]][[code]]  [[code [[/code]]\n[[/CODE]]` a recursive match exists at the first body position (which follows the opener's `]`, not a line start) whose use would close the outer body at the second closer, but the reference closes at the first, because the recursion is unavailable there. The first model let recursive matches start anywhere and diverged on exactly this shape; the shipped matcher threads the current position's line-start status through the body search (a character step sets it from the consumed character, a recursive step from the match's last consumed character), and the corrected model passes the corpus and both fuzz seeds. Two smaller tail facts are likewise modelled explicitly: the tail's `(\s|$)` tries consuming one whitespace character first, and the empty alternative exists only where the next character is a newline or the text ends, which matters for matches nested inside an outer body; and the whole match is anchored at line starts only, with the search continuing after each match's consumed span, the replacement text (`"\n\n"`, the placeholder, group 3) never rescanned.

For `getAttrs` and `stripslashes`, the edge semantics were pinned by direct probes of the reference's PHP (8.5.4) rather than assumed, and the model reproduces all of them: `stripslashes` removes a backslash before any character and emits that character (`\0` becomes the NUL character) and drops a trailing lone backslash; `getAttrs` splits on the exact two-character sequence `="` (so `type=php` and `a = "v"` both yield an empty map, the key never being assigned), takes each value up to the part's last quote through `stripslashes` (so `a="x\"y"` yields `x"y`, and an unclosed `a="unclosed` yields the empty string via PHP's `substr($v, 0, false)`), permits keys containing spaces (`foo bar="baz"`), drops a key left pending at the end, and overwrites a repeated key in place. `process()` consults `getAttrs` only when the trimmed arguments are non-empty, and appends the default `type: ""` only when no `type` key resulted.

Delimiter is mirrored as the identity, and the identity is a theorem about the model's alphabet, not an approximation: the rule fires on the literal delimiter byte 0xFF in the source, no character's UTF-8 encoding contains byte 0xFF, and placeholders in the model are structural rather than textual, so on any state reachable from decoded text there is nothing for the rule to claim (`delimiterRule_id`, proved by `rfl`). The mechanism itself exists in the reference and is only unreachable from the harness's decoded-text inputs: the byte-level probe `conformance-r3/probe-delim.php` feeds a source containing a raw 0xFF byte directly to the restricted reference (bypassing the JSON protocol, which cannot carry such a byte), and the reference claims token 0 as `["Delimiter", {"text": "\xFF"}]` and rewrites the source with the `\xFF0\xFF` placeholder (output in `conformance-r3/probe-delim-output.txt`). This matches the disposition R2 recorded from the live side.

Prefilter's whitespace-line step needed one derived fact: under `/^\s+$/m` with PCRE's greedy `\s+` (which itself matches newlines) and the multiline `$`, a match at a line start consumes the whole following whitespace run when the run reaches the end of the subject, and otherwise consumes the run up to and excluding its last newline; the mirror implements exactly that, and the frame fuzz family (whitespace and line-ending soup, including lone and paired carriage returns, vertical tabs, and ideographic and no-break spaces in the corpus) agrees with the reference on all 300 generated cases across the two seeds.
