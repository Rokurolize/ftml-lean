# REPORT-R47 — R4.7 render mirror: Code and Embed

Stage R4.7 of the render tier (R4-SCOPE staging order) is complete: the Code and Embed Xhtml render rules are mirrored in Lean on the R4.1–R4.6 pattern, the shared dispatcher now covers fifty-four rules, and every gate the brief names is green, with the stage's one external boundary (the `Text_Highlighter` library) excluded by name wherever it is reached and never passed or failed. The mirror functions live in `lean-ftml/LeanFtml/CodeEmbedRules.lean` with the new PCRE-subset engine in `lean-ftml/LeanFtml/Pcre.lean` and the transcribed allowlist in `lean-ftml/LeanFtml/EmbedPatterns.lean`; entry points and theorems are in `lean-ftml/LeanFtml/CodeEmbedRender.lean`; the driver is `lean-ftml/ConformanceR47.lean` (exe `lean-ftml-conformance-r47`); gate artifacts and the reproduction script are under `conformance-r47/` (`run_gates.sh`).

## The Code mirror and the Text_Highlighter scoping decision

`renderCode` mirrors `Text_Wiki_Render_Xhtml_Code::token` (the R2-corrected `ref-php/text-wiki/Text/Wiki/Render/Xhtml/Code.php`) under the harness configuration, in which every `css*` conf is unset, so `formatConf` yields empty interpolations and the `filename` branch is dead. The body first passes through a byte-exact mirror of `wikidotTrimCodeBody` (CRLF→LF; whole leading blank lines dropped with the first content line's indentation kept, because the loop's `ltrim` result is discarded on the failing check; trailing `" \t\n"` stripped; NBSP served as a plain space). Three branches remain, and every branch's result is wrapped in `"\n" … "\n\n"`: the trimmed body is empty under PHP `trim` (full default charlist, so a lone trailing `\r` that the code trim keeps still counts as empty), giving the bare wrapper `<div class="code"></div>`; otherwise tabs expand to four spaces, the body is escaped with `htmlspecialchars(..., ENT_COMPAT)` (exactly `RenderCore.htmlSpecialCharsCompat`), and the plain `<div class="code">\n<pre><code>…</code></pre></div>` wrapper is applied.

The recorded scoping decision the brief requires: the third branch of the PHP body, the vendored `Text_Highlighter` library, is characterized as an **external boundary**, not mirrored. The boundary is reached exactly by Code tokens whose type, lowered byte-wise, is one of the fourteen names in the PHP body's `$langs` list (`php`, `cpp`, `css`, `html`, `xhtml`, `diff`, `dtd`, `java`, `javascript`, `sql`, `perl`, `python`, `ruby`, `xml`; `xhtml` would map to the `html` grammar inside the library, and `mysql` has a grammar file in the library but is not in the list, so it takes the plain path). On that branch `renderCode` emits the stated marker bytes `\n[[UNMIRRORED:Text_Highlighter:<lowered type>]]\n\n`, and the R4.7 entry points (`renderWithR47` / `renderStateR47` in `CodeEmbedRender.lean`) scan the outcome's segment list, which in this architecture is exactly the set of tokens the render loop references, and append the name `Text_Highlighter:<lowered type>` to the outcome's `unmirrored` list for every referenced Code token reaching the boundary, so such a case is EXCLUDED with the boundary named. Boundary names are appended after any unmirrored rule names, deduplicated; in the R4.7 corpora no boundary case also references an unmirrored rule, so the append order is unobservable there. One consequence of the shared-dispatcher design is worth stating plainly: the earlier stages' entry points share `dispatchRenderR41` and therefore also render plain Code now, and a hypothetical highlighted Code token under an old entry point would emit the marker bytes and fail the byte comparison rather than pass silently; the pre-stage scan verified that no earlier corpus (notes365, prose740, the R4.2 notes prefix, and the R4.4/R4.5/R4.6 families) contains a highlighted Code token at all, every Code token in them having type `""`, so this path cannot fire in any regression gate.

The boundary is exercised by exactly nine battery cases, each carrying a single highlighted Code token, and the family gate excludes exactly those nine under the expected names: `code/arg-type-python`, `code/arg-type-PYTHON`, `code/arg-two-attrs`, `code/crlf-args` under `Text_Highlighter:python` (the `PYTHON` case confirms the lowering), `code/arg-type-css-inline`, `code/arg-tab-after`, `code/arg-multi-space`, `code/arg-newline-after` under `Text_Highlighter:css`, and `code/arg-type-name` under `Text_Highlighter:java`. The remaining fifty-three Code tokens of the family corpus are plain (type `""` or `apache`), and four code-battery cases carry no Code token at all (mid-line openers staying literal, consistent with the R2-CODE record).

## The Embed mirror and the PCRE-subset engine

`renderEmbed` mirrors `Text_Wiki_Render_Xhtml_Embed::token` (the REFVAL2-corrected file). The constructor quirk is recorded: the PHP constructor merges each globbed conf file's `$patterns` over the empty declared property, so with the tree's single conf file the effective allowlist is exactly that file's 76-entry array in file order. Those 76 pattern strings were dumped from the PHP interpreter itself (not retyped) into `conformance-r47/embed-patterns.json` and transcribed byte-for-byte into `EmbedPatterns.lean` by `conformance-r47/gen_embed_patterns.py`. The token body is: PHP-`trim` the content; test the patterns in order and take the first `preg_match` hit; strip `language="JavaScript…"` attributes globally; if the `src` attribute value, trimmed and lowered, starts with `javascript:` or `vbscript:`, render the whole embed empty; if the event-handler pattern `<[^>]*\s+on[a-z]+\s*=[^>]+>` (flags `si`) matches, or any attribute value lowered contains `javascript:` or `vbscript:`, break to the error block `<div class="error-block">Sorry, no match for the embedded content.</div>`; otherwise return the stripped content. No match also yields the error block. `renderEmbedWith` is parameterized over the pattern list so theorems can use small lists; `renderEmbed` uses the parsed 76.

The pattern engine (`LeanFtml/Pcre.lean`) implements exactly the PCRE subset the 79 patterns (76 allowlist plus the renderer's three own patterns) use, established by enumerating the constructs in the dumped strings rather than assumed: literal bytes and `.` (the `s` flag controlling `\n`), character classes with ranges, negation, and the `\s \S \d \D \w \W` escapes inside and outside classes, punctuation escapes, groups, alternation, greedy quantifiers `* + ? {n} {n,} {n,m}` with optional lazy markers (parsed and ignored: laziness never changes match existence, and the one `preg_replace` use has a deterministic extent), `^` as subject start and `$` as subject end or before one trailing `\n` (no pattern uses `m`), and the `i` flag as ASCII case-insensitivity applied by case-swapping subject bytes as well as folding literals. There are no non-capturing groups, backreferences, `\d`-style escapes outside the six listed, or POSIX classes in the corpus; `{` is a quantifier only in the valid `{n}`/`{n,}`/`{n,m}` shapes and a literal otherwise (only googlemaps' `[a-z]{2,3}` and `[0-0A-F]{6}` use it as a quantifier). Three patterns lack `^`, so the matcher implements true search semantics (all start positions, left to right). The matcher is a backtracking list-of-successes evaluator: `mEnds` returns every reachable end position in PCRE greedy preference order, deduplicated, so the head is the extent `preg_match`/`preg_replace` reports; repetition runs through `repCollect`, which bounds iterations by the subject length (every productive iteration consumes at least one byte; an empty iteration terminates the loop, as in PCRE, and still counts toward the minimum). The renderer's `src` and attribute-value regexes are implemented as hand-rolled scanners rather than through the engine, because the rule observes their captures, which the engine deliberately does not track; both patterns are deterministic at a fixed start position (literal or maximal name run, `\s*` runs, a `[^"]*` capture admit no backtracking choice), so the scanners are their exact match semantics, including `preg_match_all`'s non-overlapping left-to-right consumption for the attribute scan. The driver's `--embed-patterns-ok` mode prints `embedPatterns.length`; the gate requires exactly 76, so a pattern the parser rejected would fail visibly instead of silently narrowing the allowlist. It prints 76.
