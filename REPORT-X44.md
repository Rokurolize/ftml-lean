# REPORT-X44 — The x44 interwiki over-claim and the index-canonicalization boundary, settled (2026-11-22)

Lane: BRIEF-X44, executed 2026-11-22 in the worktree ~/workspace/ftml-lean-equivalence-x44/. Both halves of the standing x44 problem are settled against fresh live probes. The reference's Interwiki parse over-claims the described form `[site:page label]` whenever the label, as it stands when Interwiki runs, contains a token an earlier rule has already claimed or an opening bracket; live leaves the whole form literal in exactly those cases. The embedded token index in the reference's render is a pure artifact of that over-claim, not something live does: it is the unsubstituted placeholder of the claimed Url token leaking through the interwiki label, and it disappears with the claim. The reference is corrected, the corrected reference matches live on the whole probe family, and the x44 exclusion is DISSOLVED: no canonicalization is legitimate or needed. All lane artifacts are under conformance-x44/.

## 1. The probe family and what each shape decided

Twenty-six cases were designed (conformance-x44/probe-cases.jsonl, 23 cases; conformance-x44/probe-cases-2.jsonl, 3 cases) and saved on sandbox-for-codex under the prefix muse-probe-x44- (pages kept permanently). All 26 captures (conformance-x44/probe-captures.json and probe-captures-2.json) are valid, stable and source-matching. The reference side is ref-php/harness/batch.php in render and tokens modes on WSL (renders before the correction in ref-renders-before.jsonl and ref-renders2-before.jsonl, after it in ref-renders-after.jsonl; post-correction tokens in tokens-after.jsonl). Before the correction the reference agreed with live on 7 of the 26; after it, on 26 of 26 (frame comparison: the reference's trailing blank line aside, the same comparison the R2 stages use against captures).

Live's acceptance rule, as the family pins it: the described interwiki form is claimed only if the label contains neither a previously claimed token nor an opening bracket. The rejecting shapes, each served by live as the literal bracketed text with the inner tokens rendering normally: u01 `[wikipedia:X http://example.com/a]` (the x44 shape itself, re-probed; the URL linkifies inside the literal form); u02, an https URL with a query string as the whole label; u03, a URL followed by plain words; u04, plain words followed by a URL (position inside the label does not matter); u06, an email address as the whole label (rendered as the obfuscated wiki-email span inside the literal form); u17, an email address mid-label; u14, an ftp URL; u15, two URLs as the label; u16, the same URL label on the google site (the guard is not site-specific); u22, a URL with underscore, hyphen and tilde characters; u12, two URL-label forms in one document (each rejected independently); u13, a plain-label form and a URL-label form in one document (the first claims, the second goes literal, so the rule is per-form and position-independent); u18, strong markup plus a URL (rejected for the URL; the strong markup then renders normally inside the literal form, which also confirms the rejection happens at parse time, before the later rules run); u24, inline math as the label (the math span renders inside the literal form, so the guard covers every earlier-claimed token type, not only Url and Email); u26, a URL label on the unknown site prefix nosuchsite (the guard sits in the parse match itself, before any site-table question arises); and the bracket shapes u09 `[wikipedia:Albert_Einstein [x] label]` (the R2 p34 case re-probed), u10 with a bracket mid-label, and u11 with a bracket at the label's end, all fully literal on live, where the uncorrected reference claimed a truncated label (`[x`, `a [b`, `label [x` respectively). One shape sits outside the rule's reach and is recorded as observed, not as a divergence: in u25, `[wikipedia:X [[Some Page]] test]`, live serves the entire text literally including the freelink brackets, and the reference's token stream likewise contains no Freelink token for the embedded `[[Some Page]]`, so after the correction both sides serve the identical literal text; why neither side's Freelink rule claims that embedded form was not further investigated, because both sides agree byte-for-byte and no gate case depends on it.

The accepting shapes, all claimed by live and byte-identical to the reference before and after the correction: u05, a scheme-less `www.example.com/a` label (the Url rule claims nothing there, so the label is plain text); u07 and u08, strong and emphasis markup in the label (both rules run after Interwiki, so the markup is raw label text at claim time and stays literal inside the rendered link on both sides, confirming that live's architecture, like the reference's, never processes later-rule markup inside a claimed label); u19, a raw `a://b` label (an unconfigured scheme the Url rule does not claim, which kills the hypothesis that live rejects labels containing `://` as raw text); u20, an incomplete `see http://` label; u21, an uppercase-scheme `HTTP://EXAMPLE.COM/A` label (not claimed by the Url rule, accepted as text); and u23, a label containing a colon, `See: Einstein`.

The mechanism these shapes jointly identify: in the reference's pipeline the inline order is Url, Email, Mathinline, then Interwiki, so at Interwiki's turn a claimed label component is present in the source only as the placeholder byte sequence 0xFF, decimal index, 0xFF. Live behaves exactly as if its described-form match cannot cross such a placeholder or an opening bracket, which is also the shape of the fossil's own Url rule, whose described-link label class already excludes the token delimiter. The correction below adopts precisely that observable rule; no claim is made about live's internal code beyond what the shapes force.

## 2. The defect, stated precisely

Two coupled defects, both in the reference, neither in ftml (ftml has matched live on x44 since PR #1546) and neither in live:

(1) The over-claim. ref-php/text-wiki/Text/Wiki/Parse/Default/Interwiki.php matched the described form with the label pattern `(.+?)`, any bytes up to the first closing bracket. That accepts labels containing the token delimiter byte and labels containing an opening bracket, both of which live rejects as a whole-form-literal. The R2 stage recorded the URL-label half as the reference-side gap at F-R2-73 and the bracket half as the p34 coverage gap, with no rule edit; this lane discharges both.

(2) The leaked index. When the claimed label is a bare placeholder, the Interwiki token's text option is the placeholder itself, and the render emits it into the page: for a configured site, htmlspecialchars substitutes the two 0xFF bytes with U+FFFD, leaving the token's decimal index standing between them (`�702�` in the R2 batch run's retained render); for an unknown site the render returns the label before its htmlspecialchars step, so the output carries the raw bytes 0xFF, digit, 0xFF (demonstrated byte-exactly with a base64 capture of the single-case run: `<p>\xff2\xff</p>`). The index is the parse's process-global token counter, so the retained expected renders are not even reproducible by the uncorrected reference: the same source renders `�702�` in the R2 run, `�4928�` in the R4.3 family run, `�703�` in this lane's fresh uncorrected re-run of the same battery (the counter shifted by the one intervening case), and `�2�` in a single-case run. The R4.3 gate absorbed this by normalizing the digit run; that canonicalization was legitimate only as a description of the artifact, and it is not a property of live, which produces no index at any position (u12 and u13 show live's behavior is invariant across positions in a document). Once the form is not claimed, there is nothing to canonicalize.

## 3. The correction and its verification

The correction is confined to Parse/Default/Interwiki.php: the described form's label pattern is now the character class `[^\]\[\n` plus the token delimiter byte `]+`, excluding the closing bracket, an opening bracket, a newline (which the original dot pattern also excluded, so multi-line labels behave as before) and the delimiter. The standalone form, both process callbacks and the render file are untouched. Pre-correction bytes are preserved beside the corrected file as Interwiki.php.before-x44.php (SHA-256 5f47c8e77541170b172df86783b4c2cffcac6df0e295794dedb689a657f8a75e, identical to the hash the R2 interwiki SECTION.md records for the file; corrected SHA-256 ca191fa743b7b72bff0a853aeb736039a747c6e6f317046ac58f1a5ff6b10de6). The full record is conformance-refphp/inline1/interwiki/CORRECTION-X44.md.

Verification, all through the corrected reference on WSL: the 26 probe cases agree with live 26/26 (section 1); in tokens mode the rejected shapes produce only their inner Url, Email or Mathinline tokens and no Interwiki token, while an accepted plain-text label (u05) still produces its Interwiki token carrying the raw label; over the R4.3 family corpus of 1,109 cases exactly two renders move against the retained family-renders-full.jsonl, inline1-xbattery/x44 (from `�4928�`'s claimed link to a render byte-identical to the retained live capture) and inline1-interwiki/iw43-37-label-with-brackets (to a render byte-identical to the live p34 capture), and nothing else; over the R2 interwiki battery of 70 cases the only correction-attributable movement is the same iw43-37, and over the R2 interactions battery of 46 cases the only one is x44, the two other diffs against the retained files (the include error text in iw43-61 and x30, and iw43-70's trailing newline) reproducing identically with the pre-correction file swapped in, so they pre-date the correction as harness configuration and frame drift in the retained R2 artifacts and are not this correction's business; and the nine-case smoke battery is byte-identical between the pre-correction and corrected files.

## 4. Final status of the x44 exclusion and the mirror consequence

The exclusion is dissolved, not narrowed. x44's corrected reference render is byte-identical to its live capture, so the case passes the end-to-end gate on the corrected tree with no canonicalization of any kind; the digit-run normalization the R4.3 gate applied to it should be retired with the exclusion, since the only thing it ever normalized was the artifact documented in section 2. The state-mode artifacts regenerate from the corrected reference: x44's parse state loses its Interwiki token and keeps the Url token and the paragraph pair, and its expected render becomes the literal form. This lane ran no Lean builds, per its brief; the mirror consequence is stated as text for the coordinator's adoption: interwikiDescrMatch in lean-ftml/LeanFtml/Inline1Rules.lean, the parse mirror of the described form called from interwikiRule, must reject a candidate label containing the token delimiter byte or an opening bracket before constructing the token, mirroring the corrected PHP pattern exactly; renderInterwiki in InlineSimpleRules.lean needs no change, because the token it renders is never created for these shapes; the R4.3 theorems about the described form (the interwikiDescrMatch example in Inline1Rules.lean) use plain-text labels and are unaffected in statement, though the coordinator should confirm no proof steps rely on the unguarded match. Remaining named items: none for x44 itself. The u25 observation (neither live nor the reference claims an embedded `[[Some Page]]` freelink inside an interwiki label region, with both sides byte-identical) is recorded in section 1 as an agreed-behavior observation, not a remainder; if a future family needs the Freelink rule's own boundary there, it starts from that observation.
