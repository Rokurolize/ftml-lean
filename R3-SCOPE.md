# R3 scope: mirroring the validated reference in Lean

R3 is the Lean formalization of the reference implementation that R2 validated against live Wikidot (owner direction 2026-11-20: build the reference first, then take the Lean formalization from it, one Lean function per rule over the token-stream state). This document settles the mirroring target, the conformance protocol, the staging, and the claim R3 does and does not make. It was grounded by direct probes of the reference harness on 2026-11-20 (driver prototype ref-php/harness/probe-source.php, run against the canonical tree); the probe facts below are stated from those outputs, not from the fossil's documentation.

## The mirroring target: the parse-phase state pair

The reference pipeline's parse phase transforms a source string into a pair: the post-parse source, in which every claimed construct has been replaced by a placeholder consisting of the byte \xFF, a decimal token index, and \xFF again, and the token table, an ordered list of entries [rule name, attribute map] that the placeholders index into. A probe of "Hello **bold** world." gives the post-parse source "\xFF0\xFFHello \xFF2\xFFbold\xFF3\xFF world.\xFF1\xFF" with the table [Paragraph start, Paragraph end, Strong start, Strong end, then the Typography entries], which shows the two facts that define the model: token indices are assigned in the order rules claim constructs as the pipeline runs (pipeline order, then match order within a rule), and text that no rule claims stays literal in the source string, so the pair is a complete observable of the parse phase with nothing hidden. R3's Lean model is therefore a state of exactly this shape: a string with placeholders, a token table, and the small amount of document state listed below, with one Lean function per parse rule applied in the reference's pipeline order. The input to the model is the source after the harness's line-ending normalization (CRLF to LF, performed by batch.php before the pipeline; the lone-CR handling belongs to the Prefilter rule inside the pipeline, per R2-INCLUDE C1).

Four probe facts constrain the design and are recorded here so no R3 lane has to rediscover them. First, token indices are cumulative across documents inside one batch.php process (a six-case probe run numbered its documents 0-16, 17-33, 34-54, and so on), so raw tokens-mode output is not a per-document observable; the conformance protocol below canonicalizes by renumbering. Second, the Typography parse rule registers its thirteen character-substitution tokens in every document whether or not any text uses them, so the token table contains constant unreferenced entries whose positions depend on how many tokens earlier rules created; the mirror must reproduce the table exactly, not only the referenced part. Third, some rules carry document state beyond the pair: the Math rule's label-to-number map (read and written during parse, and the reason batch.php resets it per case), and the footnote and bibliography counters held in the wiki vars; the parse functions for those families take and return that state explicitly, and the first R3 stage inventories every vars entry any parse rule touches so the state record is complete by construction rather than by discovery. Fourth, constructs no parse rule claims remain literal by design and need no rule function: the double-bracket page form [[some-page|label]] is literal in the reference (the Freelink parse rule claims only the triple-bracket form, its double-bracket regex being commented out in the fossil and confirmed literal end to end by probe and render), and the mirror reproduces that by simply having no function claim it.

## What R3 claims, and what it does not

R3 claims that the Lean model implements the reference's parse phase: for every battery source, the model's final state pair equals the reference's, under the canonicalization below. Because R2 validated the reference against live Wikidot rule by rule, the Lean model thereby becomes the machine-checked form of the expected Wikidot semantics for the parse phase. R3 does not claim a structural correspondence to ftml's AST: ftml tokenizes and builds a tree by its own design, and no token-stream-to-AST mapping is defined or needed. ftml's equivalence to the same semantics continues to be carried by the R2 render differentials and the gap ledger, where every residual difference is a numbered finding with a disposition, and by the Tier 1 Lean families, which prove ftml's own algorithms directly for the families they cover. A future bridge that maps token streams to ftml ASTs per construct could strengthen the link, but it is not R3 scope and no R3 stage waits on it. The render phase (the Xhtml rules, and with them the Stage 2 purifyHtml re-nesting that the 2026-11-04 ruling assigns to Tier 2) is likewise out of R3 scope, consistent with the standing parse-only spec decision: R3 mirrors parse rules only, including parse rules whose effects complete only at render (Typography registers its tokens at parse; the substitution itself is render and stays out).

## Conformance protocol

Each R3 stage generates its expected states from the canonical reference tree with a state driver (probe-source.php is the working prototype; R3.1 promotes it into the harness as a disclosed addition alongside batch.php, in the same manner as the earlier disclosed harness changes). The comparison canonicalizes both sides identically: token indices in the post-parse source and the token table are renumbered per document in table order starting from zero, attribute maps are compared as unordered key-value sets with values compared as strings after JSON round-trip, and the Typography constant entries are compared as part of the table like any other entry. A stage's conformance corpus is its R2 battery sources plus its interaction battery, which already exist and already carry live validation; no new live probing is needed for R3 unless a stage finds the reference and its own R2 record disagree, in which case the evidence order applies and the discrepancy is reported before any modelling decision. A rule family is MIRRORED when its Lean functions build under the project's axiom discipline and its conformance slice is byte-exact under this protocol; where a rule admits a clean algebraic characterization, theorems are proved as in Tier 1, and where it does not, exhaustive battery conformance is the evidence, following the G1.6 precedent and stated as such in the stage record.

The main cost driver is stated plainly: the PHP rules are PCRE-regex-driven and Lean has no regex engine, so each rule's matching behavior is modelled as an explicit scanner, following the Tier 1 precedent (the Include scanner and the ParagraphStack formation core). The R2 per-rule SECTION.md files, which already describe each corrected rule's behavior in prose settled by live captures, are the modelling briefs; a lane never models from the fossil's regex alone without the section and its battery. Regex-heavy families (Table, Image, Module) are sequenced after the scanner-friendly ones so the scanner toolkit (shared character-class, run, and pairing helpers in the Lean project) is built and proven on simpler rules first.

## Staging

R3 reuses the R2 stage boundaries, whose batteries and sections already exist, in pipeline order: R3.1 builds the infrastructure (the state type, the pipeline runner, the state driver and comparison tool, the scanner toolkit's first helpers) and mirrors the frame rules and the Code family end to end as the proving run, since Code's parse is small and its battery is already byte-settled; then Form/Raw/Rawold, the Module family, the NEXT family (Iftags, Comment, Iframe, Date, Math, with the equation-map state), the LINK family (Concatlines, Freelink, Equationreference), the NOTES family (with the footnote and bibliography state), BLOCK, CONTAIN, LIST, TABLE, PARA, and the three INLINE stages, closing with Tighten. Tier 1 already covers Include and the G1.5 paragraph-formation core in their own terms; R3 does not redo them, and the Paragraph rule's mirror reconciles with G1.5's model when the PARA stage arrives, recording any difference between the two models as a finding against one of them. The recorded reference remainders (the missing [[ul]]/[[ol]]/[[li]] block rule M46, the Anchor-rule gap, and the render-level Include missing-page message) stay out of R3's stages, since R3 mirrors the reference as validated; each remains in the ledger for its own later pass.

## Definition of done for the tier

R3 is complete when every parse rule of the validated reference is MIRRORED under the protocol above, or carries a recorded evidence-based disposition in the gap ledger, the same exhaustion standard as the rest of the loop. The first execution step is the R3.1 brief (infrastructure plus frame and Code), to be written against this scope when a vehicle is available; until then this document is the loop's R3 record.
