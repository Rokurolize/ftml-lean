## 2. What is now proved or certified

The flat draft was split into a four-module proof set plus an umbrella, all in lean-ftml/LeanFtml/: ProofEmailKeepers.lean (the audited keepers and their helpers), ProofEmailDigits.lean (decimal/parse mechanics: emailIsDigitByte, digitsVal, digitsVal_append_single, digitsVal_decBytes, takeWhile_eq_self_append_cons, takeWhile_decBytes_255, drop_prefix_append), ProofEmailRenumber.lean (the byte-level TokEquiv projection: tokGo, tokRenumberBytes, tokGo_id_of_no_ff, tokGo_ph, tokRenumberBytes_phBytes, EmailTokEquiv, email_tok_equiv_base_shift), ProofEmailObserver.lean (the showcase), and ProofEmail.lean (umbrella importing the four; the coordinator wires this file or the siblings into LeanFtml.lean at adoption).

The three keepers are established as theorems: decBytes_safe (decimal bytes are ASCII and exclude escape, pipe and delimiter bytes), htmlSubst_safe (htmlSpecialCharsNoQuotesSubst reduces to flatMap of U+FFFD on 0xFF and identity elsewhere over the safe-byte predicate), and renderEmail_claimed_placeholder (exact byte-level output for one claimed placeholder with arbitrary address and surrounding label bytes). digitsVal_decBytes proves digitsVal (decBytes k) = k by strong induction, so the scanner reindexes decimal placeholder digits without an unverified parser.

The byte-level TokEquiv projection is local to this lane: tokGo is a fueled scanner that recognises \xFF<decimal>\xFF runs and rewrites their index by σ with fuel bs.length + 1; tokRenumberBytes_phBytes gives the exact projector tokRenumberBytes σ (pre ++ phBytes k ++ post) = pre ++ phBytes (σ k) ++ post for 0xFF-free pre and post; EmailTokEquiv is the Email-facing alpha-equivalence on OptMaps (same address bytes, text label reindexed by σ) and email_tok_equiv_base_shift instantiates it for σ(j) = base + j. This is §5.2's TokEquiv treatment expressed concretely at the byte level; it does not depend on the absent coordinator F1 kernel.

The showcase is email_index_observer_law (base k): under cumulative-base renumbering σ(j) = base + j, an Email claim for token k renders the same wiki-email span, reversed address, literal #, preserved surrounding label bytes, and exactly utf8Fffd ++ (decBytes (base + k)).reverse ++ utf8Fffd between two reversed literal fragments. The claimed index is observed, not hidden. email_index_observer_plus_one proves both the byte-level reindexing and the rendered digit run under σ(j) = j + 1 are exactly index k + 1, so the owned +1 counter class inside U+FFFD is the base = 1 instance of the same law and is accounted for formally rather than routed around or masked. email_renumber_index_injective proves the additive shift is injective on claimed indices, so the relation is an alpha-equivalence rather than a collision-prone hash. For base = 0 the law specialises to the canonical per-document reference.
