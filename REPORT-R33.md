# R3.3 report: the $bytes wire encoding (Part 1) and the Module family mirrors (Part 2)

Stage R3.3 ran in the order the brief specifies: Part 1 retired the PASS-UNREPRESENTABLE verdict by strengthening the conformance protocol, with its regression gate over the R3.2 artifacts; Part 2 then mirrored Modulepre, Module, and Module654 against the nine-rule restricted oracle. Both parts pass every gate the brief lists. No formerly unrepresentable case disagreed by content, so Part 1 produced no finding, and the Part 2 corpus needed no exclusions. The final corpus is 204 cases (modulepre battery 55, module battery 52, module654 battery 59, interaction battery 29, smoke 9), and the Lean model matches the restricted reference on all 204, on 1,000 seeded fuzz cases, and on the full R3.1 and R3.2 regression slices re-run with their own drivers.

## Part 1: the protocol change

The weakness, as R3.2 recorded it: a token option value whose bytes are not valid UTF-8 (in this pipeline, exactly a claimed text spanning an earlier rule's placeholder, so containing the delimiter byte 0xFF) made the PHP state driver's `json_encode` fail for the whole case; both drivers emitted an identical error record, and the comparison counted error-on-both-sides as PASS-UNREPRESENTABLE, a verdict with no content evidence, which covered 55/500 default-seed and 50/500 seed-7 fuzz cases in R3.2.

The change is at the serialization layer only, applied identically on both sides, and the reference's behavior is untouched. In `ref-php/harness/state-restricted.php`, a recursive `ref_wire_encode` now walks the output structure before `json_encode` and replaces any string that is not valid UTF-8 (tested with `preg_match('//u', ...)`) with `{"$bytes": [b0, b1, ...]}`, the list of its byte values; array keys are not transformed, because every key in the output structure is created by the driver itself or is a parse rule's option name, all ASCII identifiers. On the Lean side, `serOptVal`'s `bytes` case in TokenState.lean applies the same rule: a byte string that is valid UTF-8 (the new strict `utf8Valid` predicate, which rejects overlong forms, surrogate halves, stray continuations, and codepoints above U+10FFFF, matching the PHP test) crosses as the JSON string of its decoding, and any other byte string crosses as the `$bytes` object. The identical-error-record interception is removed from ConformanceR32.lean, which now simply serializes every state, as R3.1's driver does. The stage's new comparison tool (conformance-r3/compare.py) decodes the `$bytes` shape back to a byte string and renumbers placeholder references inside it (delimiter byte, decimal id, delimiter byte) through the owning record's own per-document token renumbering, exactly as segment references are renumbered; the PHP side's process-global ids and the Lean side's per-document positions therefore canonicalize to the same byte string. An error record on either side is now a failure (FAIL-ERROR): after the encoding, no content-bearing state can produce one.

The injectivity argument: the encoding is a function of the byte content alone, and it is injective on the value space the protocol carries. Two distinct valid-UTF-8 byte strings decode to two distinct JSON strings, because UTF-8 decoding is injective on valid encodings. An invalid byte string's encoding is a single-key object holding a list of integers 0–255, which is distinct from every JSON string and from every other byte list. The one theoretical collision, a genuine option map that itself has the single key `$bytes` with a bare integer-list value, cannot occur: option keys across the reference's parse rules are fixed ASCII identifiers chosen by the rule authors (the addToken call sites use keys such as moduleName, attr, module_body, text, blank, char, type, title, id), no rule builds a `$bytes` key, and no rule builds a bare integer-list option value; a grep over the reference tree confirms `$bytes` appears nowhere in it. One supporting move: `utf8Decode` and `isContByte` moved from FormRawRules.lean into TokenState.lean, because the serializer now needs the decoder; FormRawRules uses them through the import, unchanged.

The gate re-ran R3.2's fuzz families (inputs and generator in conformance-r3-prev/) and the whole R3.2 corpus under the strengthened protocol, with the PHP side regenerated by the strengthened driver and the Lean side by the rebuilt ConformanceR32 driver. Every formerly PASS-UNREPRESENTABLE case now compares by content and passes: 55/55 on the default seed (20261120) and 50/50 on seed 7, verified case by case against the verdicts recorded in conformance-r3-prev/comparison-fuzz.txt and comparison-fuzz-s7.txt; no other case's verdict changed on either seed. Because no formerly unrepresentable case disagreed by content, there is no hidden-defect finding to record and the gate does not block; the R3.2 mirrors are confirmed by content on the cases the weak verdict used to cover. ## Part 2: the mirrors

The three mirrors live in lean-ftml/LeanFtml/ModuleRules.lean, written from the corrected rule files with conformance-refphp/R2-MODULE.md, the per-rule SECTION.md files, and CORRECTION-F13.md as the correction record. All three share one opener head (moduleHead): the rule's literal matched case-insensitively, one whitespace byte, a maximal name run over the name character set, and the attribute group enumerated as the increasing list of `]]` positions the lazy group can end at, in PCRE priority order; the first candidate whose tail matches decides the match, which is exactly PCRE's backtracking order, and the enumeration argument (the name run never needs to backtrack, the group-present and group-absent cases are disjoint on the byte after the name, and `]]` candidates start one byte into the whitespace run because the group's `\s+` must consume at least one byte) is recorded in the file's comments. The tails differ as the corrections require: Module admits spaces only before the newline and its body group is `(.+?)`, so the closer search starts one byte into the body (an immediate closer is the body's first byte, and with no later closer the group does not participate, correction C2); Module654 admits tabs as well (correction C1) and its body group is `(.*?)`, so an immediate closer gives an empty participating body. Modulepre claims nothing and returns the match with its leading `[[module654` rewritten to `[[module` by the reference's case-sensitive replacement, an opener matched only through case folding keeping its spelling, with the optional body group extending the match to the first closer whenever one exists later. Module's process() defense is reproduced exactly: the matched text is rescanned by countModuleOpeners (preg_match_all of the opener-only pattern at line starts, non-overlapping), and a count above one returns the match with its leading `[[module` rewritten to `[[module654` and claims nothing; otherwise one Module token is claimed with trimmed attr and body, replaced by "\n\n" around the placeholder. Module's parse() loop is mirrored as passes to the source fixpoint, with the pass bound argued from the strictly decreasing count of `[[module`-plus-whitespace occurrences. Module654 claims the same option shape in a single pass, with no defense. CORRECTION-F13.md's nested-opener consumption rule is not a special case anywhere in the mirrors: it falls out of the composition (Modulepre's rewrite, Module's loop plus defense, Module654's plain claim), as the correction record says it falls out of the reference's own mechanisms, and the xbattery cases pin it.

Per-rule byte-form analysis, as the brief requires. All three rules run after token-producing rules, so all three mirrors work on the byte form through applyByteRule, the R3.1 obligation. A match can never start or end inside a placeholder, for any of the three: match boundaries are the ASCII opener literal at a line start, `]]`, a newline, and the ASCII closer literal; a placeholder contains none of those bytes and no newline, so no line start falls inside one either. Attribute strings and bodies can and do span whole placeholders: a Raw placeholder can sit in an opener line's attribute area, and Code, Form, and Raw placeholders sit routinely inside bodies, the xbattery's nested shapes being exactly this (an inner module claimed in an earlier pass leaves its placeholder inside the outer match's body). Such values are OptVal.bytes and, since Part 1, compare by content. The defense's opener count runs over the matched byte text, placeholders included; a placeholder contains no `[` byte, so it can neither open nor hide an opener head, and the count needs no placeholder awareness. The evidence settling these points is the corpus itself (the interaction battery's 29 cases include placeholder-spanning bodies and attrs, all agreeing by content), the two fuzz families aimed at the same shapes (fz-mix-* assemblies with code, form, and raw constructs inside bodies and attribute areas; 81 records on the default seed and 87 on seed 7 carry `$bytes` values, with identical counts on both sides), and the nine formerly unserializable fixture records discussed under the consistency check.

On the ModuleManager stub: the R2 stub in ref-php/harness/ozone-stubs.php (nine known names) is part of the reference as adopted and the restricted oracle inherits it unchanged, but no mirror's behavior depends on its name list, because no parse rule consults ModuleManager or canWikiUseModule at all (verified by grep over ref-php/text-wiki/Text/Wiki/Parse/Default/); the stub is render-side only, and the parse phase this stage mirrors never calls it.

Three theorems were added, all proved by rfl and audited in Main.lean: modulepreRule_tokens (Modulepre's mirror leaves every state's token table unchanged), moduleMatch_defense_example (the smallest nested shape is rewritten, not claimed, with the table untouched), and module654Match_claim_example (a plain Module654 claim with its trimmed options and "\n\n"-wrapped placeholder). Each depends on axioms [propext, Classical.choice, Quot.sound], the choice coming in transitively through the definitions unfolded, as with R3.2's rawScan_no_at; none depends on sorryAx.

## The consistency check, and the nine missing fixture records

The pre-seeded full-pipeline fixtures turned out to be missing exactly nine records: mp-nested-module-in-654 and mp-nested-654-in-module from the modulepre file (53/55 present), mod-nested-two-openers and mod-nested-unknown-in-body from the module file (50/52), and x-654-body-module, x-654-body-module-attr, x-mod-body-654, x-mod-in-mod, and x-known-mod-body-654 from the interaction file (24/29); the module654 file is complete at 59/59. The missing nine are precisely the F13 nested shapes whose module_body spans an earlier placeholder, which probe-source.php's plain json_encode could not serialize, the same gap Part 1 closed in the state driver. The remedy, disclosed here as the brief's disclosure rule requires: a one-off prefix driver (ref-php/harness/prefix-source.php, modeled on probe-source.php's construction and the state driver's output format) ran the ten-rule full-pipeline prefix (Include, then the stage's nine) under the full wiki configuration and page map; rules after the prefix cannot create, remove, or mutate claims inside it, because the token table is append-only during parse and no parse rule edits another rule's token options, so the prefix record is the full pipeline's own record for the family's claims. The checker (conformance-r3/consistency_check_r33.py) first validated that surrogate: the prefix run's Module/Module654 claim sequences agree with the pre-seeded fixtures on all 186 cases the fixtures carry (summary A: 186/186). Only then was it used as the full side for the nine missing cases (and for the nine smoke cases, which have no pre-seeded fixture in this worktree). The consistency verdict proper: the restricted nine-rule oracle's family claim sequences agree with the full side on all 204 cases (summary B: 204/204 consistent), so the stage corpus has zero exclusions; as supporting evidence, the restricted and prefix runs also agree on the earlier rules' claims (Code, Form, Raw, Rawold) on all 204 cases (summary C: 204/204), so on this corpus Include's upstream presence perturbs nothing the stage compares. The R2 coverage gap stands as recorded and was not probed in this stage: four Module654 probe pages (p-upper-nested, p-upper-inline-empty, p-control-module, p-control-plain) remain uncaptured.

## Conformance, fuzz, and regression results

The stage corpus is 204 cases with no exclusions: the modulepre battery (55), the module battery (52), the module654 battery (59), the interaction battery (29), and the smoke set (9). The Lean R3.3 driver (pipelineR33, the nine rules in reference order) matches the restricted reference on all 204 (conformance-r3/comparison-module.txt: SUMMARY 204/204). The fuzz differential (conformance-r3/fuzz_r33.py; families fz-mod-* structured block assemblies at the head, tail, body, and defense edges, fz-pre-* Modulepre placements and case variants, fz-mix-* placeholder-spanning mixtures) passes 500/500 on the default seed 20261120 and 500/500 on seed 7. The regression slices pass with their own drivers: R3.2's corpus and fuzz were re-run as the Part 1 gate above (68/68, 9/9, 500/500, 500/500), and R3.1's slice was re-run in full with the rebuilt ConformanceR31 driver against the strengthened three-rule oracle (code battery 68/68, smoke 9/9, fuzz 500/500 on the default seed and 500/500 on seed 7; the R3.1 fuzz inputs were read from the canonical record, as R3.2's stage read its corpus inputs). The whole Lean project builds green: `lake build` completes successfully (50 jobs) and all executables including the three R3 drivers build (58 jobs), with the elan PATH prefix. A grep for `sorry` over the new and edited Lean files (ModuleRules.lean, TokenState.lean, Pipeline.lean, ConformanceR32.lean, ConformanceR33.lean) finds no occurrence outside the word sorryAx, and the three new theorems' axiom audits are recorded above.

One spot check worth citing: x-mod-in-mod, the signature F13 shape, produces on both sides a Module token for the inner module and a Module654 token for the defense-rewritten outer one whose module_body is the byte string "outer\n\n\n" plus the inner token's placeholder; the two sides' `$bytes` lists are identical except the placeholder's id (164 in the reference's process-global numbering, 0 in the model's per-document numbering), which the comparison's renumbering canonicalizes, so the case passes by content, the exact behavior the retired verdict used to wave through unevidenced.
