## The compared-state disposition: no extension for headline_id

The brief left the `headline_id` question open: Heading's process maintains the counter in the wiki vars, and Toc reads Heading's products, so the counter might have needed to join the compared state the way Math's equations map and id did in R3.4 and the notes vars did in R3.6. The evidence says it does not. A grep over the whole reference tree (`ref-php/text-wiki` and `ref-php/harness`, the fossil excluded) finds exactly one reader or writer of `vars['headline_id']`: `Parse/Default/Heading.php` itself, which initializes it to 0 on the first heading match and increments it per plain heading. Toc never reads the var; its process reads the token table through `getTokens('Heading')`, the R3.5/R3.6 table-read pattern, which the compared state's token table already covers. Neither the pre-seeded full-pipeline fixtures (their record keys are exactly `id`, `post_parse_source`, `tokens`) nor the state driver's output carries a headline field, so no PHP-side serialization of the counter exists to mirror. The counter's whole observable effect is the `id` option on Heading start tokens (`toc0`, `toc1`, … in match order), which the token comparison already covers; the final counter value is additionally determined as the count of plain Heading start tokens. The mirror therefore maintains the counter internally, in the `DocState.headlineId` field that has existed since R3.1, and serializes nothing new. `DocState` and the wire protocol are untouched this stage; `compare.py` is the R3.6 copy with a header note, comparing the R3.6 field set unchanged, with records lacking a field read as that field's empty value.

## The rules as modelled

All three rules run on the byte-form view of the state (the recorded R3.1 obligation: every rule after the first token-producing rule is written against byte form), because all three patterns can span placeholders left by earlier rules, and two of the three provably meet them in the corpus. The per-rule analysis is in the header of `LeanFtml/BlockRules.lean`; the load-bearing facts are these. Blockquote's options carry only a type and a level, never text, so placeholder claims inside a quote body cannot change its claim sequence; its captured run, though, is delimited by where placeholders sit, and its claimed regions are spliced back as text around its own tokens, so the scan is byte-level. Heading's group-3 text stays literal between its start and end placeholders and can span an earlier placeholder (a footnote claimed inside a heading line is the battery's shape), so the stored text goes through `textVal` and becomes a byte string exactly when it spans a claim. Toc's attribute values can hold a placeholder (through `textVal` in the shared getAttrs port), and the item texts it splices are the Heading tokens' stored texts carried through verbatim, so its walk reads the byte form of the text options via a small `optValBytes` view.

Blockquote is a `preg_replace_callback` scan whose outer pattern (`/\n((\>).*\n)(?!(\>))/Us`) captures a maximal run of `>`-led lines: a match consumes a leading newline, the run's first line starts with `>`, and the run ends at the first newline whose following byte is not `>` — which means a quote run whose last line has no trailing newline never matches at all, a shape the battery pins (Prefilter's appended newlines are what make ordinary quotes match). The captured run is re-scanned by an inner line pattern (`=^(\>+) (.*\n)=Ums`) that claims only lines carrying a literal space after the marker run; non-matching lines inside the run are consumed and dropped. The process walks the matched lines with a depth stack: with correction C2, a run whose matched lines are all empty (or which has no matched lines) is consumed but claims nothing and returns two newlines; otherwise a push phase emits, per new depth, a newline, a start token, and two newlines, with every start token of the phase carrying the line's level minus one (the battery's depth-skip case pins starts at levels 0, 2, 2 for lines of level 1 then 3); a pop phase emits two newlines, an end token carrying the stack depth after the pop, and — correction C3 — two further newlines; the last line drains the stack with end tokens at descending levels and no separators. The `[[blockquote]]` block form is literal on live and stays literal here by the pattern's own limits: no pattern in the mirror matches it.

Heading is a line-anchored scan (`/^(\+{1,6})(\*?)[ \t]+(.*)/m`): one to six pluses (a line with seven or more never matches on any backtracking path, since the seventh plus is neither the optional star nor a space), the star tried consumed first, the space/tab run consumed whole, and the rest of the line as the text. The process initializes `headline_id` to 0 on any match, even in a document whose first heading is a notoc one; a plain heading takes the id `toc` concatenated with the counter and increments it, while a star heading claims the distinct `start-notoc` type with a null id and does not increment. The replacement is a newline, the start placeholder, the literal text, the end placeholder, and two newlines, with the line's own trailing newline left in place after it.

Toc is a `preg_replace_callback` scan (`/^(?:\n*)\[\[(f[<>])?toc(.*)?\]\](\n)*/m`, no case-insensitive modifier, so `[[TOC]]` is literal) whose process reads the token table at parse time — settled from the rule file, against the render-time reading one might have assumed. The leading newline run is effectively maximal, since giving a newline back would put it where the `[[` must stand. The tail group `( .*)?` is tried present before absent; present, its `.*` is confined to the line and backtracks to the LAST `]]` on it, so a quoted `]]` inside an attribute value is consumed into the group (the R2 probe p05-quoted-close's shape, re-pinned by the stage fuzz). The process claims a list_start token (type, level 0, the getAttrs map of the trimmed tail group, the align value), then walks every Heading token in table order at match time — including end tokens, which it skips by an exact `type == 'start'` test, and including headings claimed after the `[[toc]]` in the source, since Heading ran earlier in the pipeline — claiming per start token an item_start (the heading's id option passed through as the stored value, its level, and a count restarting at 0 per process call), a verbatim splice of the heading's stored text bytes, and an item_end; a list_end closes the claim. Multiple `[[toc]]` matches each re-walk the same Heading list. The `currentFormat == 'xhtmleditable'` early return never fires in a parse context (the format is set only when rendering begins, and then to `Xhtml`; in the state driver it is null), so it is not modelled. Two reference behaviors in this rule were pinned by the corpus only during this stage, and both are now documented in the mirror. First, the align value is null — not the empty string — when neither the tail group nor the trailing-newline group participated in the match: PHP fills an unmatched capture group with `''` only when a higher group is set and omits trailing unmatched groups from `$matches` entirely, so `'align' => $matches[1]` reads an absent index exactly for a `[[toc]]` followed by same-line text or by nothing (battery cases toc73-same-line-text and toc74-clear-float); when the tail group participated or at least one trailing newline was consumed, align is the float literal or `''`. The attribute map is unaffected by the distinction, since an absent tail group yields an empty map either way. Second, the tail group's `.*` cannot cross a newline, so the closing `]]` is the last one on the opener's own line; an earlier draft of the mirror searched the whole remaining source and swallowed a later line's `]]` into the group on the x battery's two-toc case (x-toc-attr), which the corpus caught.

## Consistency check

The consistency check (`conformance-r3/consistency_check_r37.py`, output in `conformance-r3/consistency-r37.txt`) follows the R3.6 three-summary shape, with one structural difference the brief anticipated: the BLOCK family is not consecutive with the earlier mirrored families in the full pipeline, because the still-unmirrored Divprefilter, Anchor, and User rules sit between Bibcite and Blockquote in the Text_Wiki default rule list. The faithful stand-in for the full pipeline is therefore the TRUE prefix through Toc — thirty rules: the twenty-six mirrored rules plus Include (which runs first in the full pipeline and claims nothing on any battery case here) and the three interposed rules — generated by `ref-php/harness/prefix-source.php` from the worktree's reference, and summary A validates that stand-in against the pre-seeded full-pipeline fixtures before anything rests on it. Summary A (prefix vs fixture, family tokens): 197/197 agree — the prefix run is a faithful stand-in for the full pipeline on BLOCK claims, and in particular the interposed rules do not touch the family's claims on the fixture corpus beyond the one case summary B isolates. Summary B (restricted oracle vs full pipeline, family tokens): 205/206 consistent, with exactly one exclusion, recorded here and in the checker output: case h18-anchor, whose heading line contains a `[[a name="x"]]anchor[[/a]]` element that the interposed, still-unmirrored Anchor rule claims in the full pipeline before Heading runs, so the full side's Heading text option is the placeholder-spanning byte string for the anchor span while the restricted side's is the literal source text; the exclusion is from the consistency corpus only, and the Lean-vs-restricted conformance below covers h18-anchor itself on all 206 cases. The interposed rules' other sensitivities were checked and do not arise in the batteries: Divprefilter fires on no BLOCK case, no `[[user ...]]` shapes occur, and the anchor-shaped lines in toc50 claim Anchor tokens in the full pipeline without touching any BLOCK claim sequence. Summary C (restricted vs prefix, earlier rules): 206/206 agree, no case skipped — the thirteen earlier token-producing rules claim identically in the restricted and prefix runs across the whole corpus. The nine smoke cases ride in the corpus with the prefix run as their full side, as in R3.6, since no pre-seeded fixture covers them. The final BLOCK corpus is 206 cases: the blockquote battery (50), the heading battery (55), the toc battery (56), the BLOCK cross battery (36), and the smoke battery (9).
